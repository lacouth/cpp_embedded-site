    4. Máquinas de estados¶

    Vídeo

    Ainda não há vídeo para este capítulo.

    Um semáforo fica verde, depois amarelo, depois vermelho, e volta ao verde. Um botão está solto, depois talvez apertado, depois apertado de verdade. Os dois são exemplos do padrão mais usado em firmware: a máquina de estados. Neste capítulo ela vira uma classe, com enum class para os estados e switch para as regras. No fim, o botão que quicava no capítulo 2 fica resolvido de vez.

    O semáforo do jeito ingênuo¶

    Com o que se sabia no capítulo 1, um semáforo sai assim:

    void loop() {
    verde.liga();     delay(5000); verde.desliga();
    amarelo.liga();   delay(1000); amarelo.desliga();
    vermelho.liga();  delay(3000); vermelho.desliga();
}

    Funciona até alguém pedir um botão de pedestre que encurte o verde. Durante o delay(5000) o botão não é lido, e mesmo que fosse, o programa não teria como "pular" para o fim da espera. O capítulo 3 já ensinou a trocar a espera por consultas ao relógio. O que falta é um jeito organizado de lembrar em que fase o semáforo está e decidir, a cada volta, se é hora de mudar.

    Estados, transições e eventos¶

    Uma máquina de estados tem três ingredientes:

    • estados: as situações possíveis, uma de cada vez (verde, amarelo, vermelho);
    • transições: as regras de mudança ("do verde vai para o amarelo quando...");
    • eventos e condições: o que dispara uma transição (o tempo na fase passou de 5 s; o pedestre apertou o botão).

    Antes de escrever código, desenhe. O semáforo com pedestre fica assim:

                  passou 5 s, ou
       (pedido e passou 1 s)        passou 1 s
  ┌───────┐ ───────────────► ┌─────────┐ ──────────► ┌──────────┐
  │ VERDE │                  │ AMARELO │             │ VERMELHO │
  └───────┘ ◄─────────────────────────────────────── └──────────┘
                           passou 3 s
                    (o pedido é atendido ao entrar no vermelho)

    O desenho já responde perguntas que, no código, viram bugs: o pedido de pedestre durante o vermelho faz alguma coisa? (Não na hora: só o verde olha o pedido. Ele fica anotado e encurta o próximo verde.) E um pedido durante o amarelo? (É esquecido ao entrar no vermelho: a travessia já vai acontecer.) O verde pode durar menos que 1 s? (Não: o mínimo vale mesmo com pedido.)

    Os estados como enum class¶

    enum class Fase { Verde, Amarelo, Vermelho };

    O enum class (do capítulo 3 do C++ do Zero) é perfeito para estados: uma variável Fase só pode valer uma das três opções, e o compilador não deixa misturar com int sem querer. fase_ == 1 não compila; fase_ == Fase::Amarelo é a única forma de perguntar.

    A classe Semaforo¶

    const unsigned long TEMPO_VERDE_MS = 5000;
const unsigned long TEMPO_VERDE_MINIMO_MS = 1000;   // mesmo com pedido de pedestre
const unsigned long TEMPO_AMARELO_MS = 1000;
const unsigned long TEMPO_VERMELHO_MS = 3000;

class Semaforo {
private:
    Led verde_;
    Led amarelo_;
    Led vermelho_;
    Fase fase_;
    unsigned long entrou_ms_;   // quando entrou na fase atual
    bool pedido_;               // um pedestre pediu para atravessar

    // Unico lugar que troca de fase: acende o LED certo e marca o tempo.
    void entra(Fase nova) {
        fase_ = nova;
        entrou_ms_ = millis();
        verde_.desliga();
        amarelo_.desliga();
        vermelho_.desliga();
        switch (nova) {
            case Fase::Verde:    verde_.liga();    break;
            case Fase::Amarelo:  amarelo_.liga();  break;
            case Fase::Vermelho: vermelho_.liga(); pedido_ = false; break;
        }
    }

public:
    Semaforo(int pino_verde, int pino_amarelo, int pino_vermelho)
        : verde_(pino_verde), amarelo_(pino_amarelo), vermelho_(pino_vermelho),
          fase_(Fase::Verde), entrou_ms_(0), pedido_(false) {}

    void inicia() {
        verde_.inicia();
        amarelo_.inicia();
        vermelho_.inicia();
        entra(Fase::Verde);
    }

    // Evento: o botao do pedestre foi apertado.
    void pede_travessia() {
        pedido_ = true;
    }

    // Chame a cada volta do loop(): decide se e hora de trocar de fase.
    void atualiza() {
        unsigned long na_fase = millis() - entrou_ms_;

        switch (fase_) {
            case Fase::Verde:
                if (na_fase >= TEMPO_VERDE_MS ||
                    (pedido_ && na_fase >= TEMPO_VERDE_MINIMO_MS)) {
                    entra(Fase::Amarelo);
                }
                break;

            case Fase::Amarelo:
                if (na_fase >= TEMPO_AMARELO_MS) {
                    entra(Fase::Vermelho);
                }
                break;

            case Fase::Vermelho:
                if (na_fase >= TEMPO_VERMELHO_MS) {
                    entra(Fase::Verde);
                }
                break;
        }
    }

    Fase fase() const {
        return fase_;
    }
};

    Quatro decisões de projeto que valem para toda máquina de estados deste curso:

    1. Um case por estado, olhando só para as saídas dele. O case Fase::Amarelo não sabe nada de pedestre. Cada pedaço do switch é pequeno e responde a uma pergunta só: "estando aqui, para onde vou?".
    2. Um único lugar troca de estado: entra(). Mudar a fase, apagar os LEDs, acender o certo e marcar o tempo andam sempre juntos. Se cada case fizesse isso por conta própria, bastaria esquecer o entrou_ms_ = millis() em um deles para a fase seguinte durar zero. entra() é privado: só a própria classe troca de fase.
    3. O evento só registra; quem decide é atualiza(). pede_travessia() não troca de fase, só anota pedido_ = true. A decisão continua concentrada no switch, onde está a regra do verde mínimo.
    4. Composição de novo. O Semaforo tem três Led e usa só a interface pública deles, como o Pisca do capítulo 3.

    Método privado

    Até aqui, todo método era public. entra() é uma peça interna: ninguém de fora deveria poder trocar a fase, senão o invariante "o LED aceso corresponde a fase_" estaria à mercê de qualquer um. Métodos privados são ajudantes da própria classe.

    No computador, com o "loop" rodando de 100 em 100 ms (exemplos/cap04_semaforo.cpp):

    so o tempo:
  t=5000 ms -> amarelo
  t=6000 ms -> vermelho
  t=9000 ms -> verde
pedestre aperta em t=10500:
  t=10600 ms -> amarelo
  t=11600 ms -> vermelho
  t=14600 ms -> verde

    Sem pedido, o verde dura 5 s. Com o pedido em t=10500, o verde (que começou em 9000 e já tinha passado do mínimo de 1 s) termina na volta seguinte.

    Debounce: o botão também é uma máquina de estados¶

    No capítulo 2, o botão do Wokwi quicava: um aperto virava dezenas de bordas. A observação que resolve o problema é simples: o quique dura pouco. Se a leitura ficar parada no mesmo valor por, digamos, 30 ms, é um aperto de verdade. Se mudar antes disso, é quique.

    Isso é uma máquina de estados com quatro estados:

                    lido apertado                         firme por 30 ms
  ┌───────┐ ──────────────────► ┌────────────────┐ ───────────────► ┌──────────┐
  │ SOLTO │                     │ TALVEZ APERTADO│    (CLIQUE!)     │ APERTADO │
  └───────┘ ◄────────────────── └────────────────┘                  └──────────┘
      ▲         lido solto (era quique)                                  │
      │                                                                  │ lido solto
      │  firme por 30 ms        ┌──────────────┐                         │
      └──────────────────────── │ TALVEZ SOLTO │ ◄───────────────────────┘
                                └──────────────┘ ───► APERTADO, se lido apertado (era quique)

    O clique é anunciado na transição de "talvez apertado" para "apertado", e só nela.

    // Quanto tempo a leitura precisa ficar parada para ser levada a serio.
const unsigned long ESTAVEL_MS = 30;

enum class EstadoBotao { Solto, TalvezApertado, Apertado, TalvezSolto };

class BotaoFiltrado {
private:
    const int pino_;
    EstadoBotao estado_;
    unsigned long desde_ms_;   // quando a leitura mudou pela ultima vez
    bool clique_;              // houve clique NESTA volta?

public:
    explicit BotaoFiltrado(int pino)
        : pino_(pino), estado_(EstadoBotao::Solto), desde_ms_(0), clique_(false) {}

    void inicia() {
        pinMode(pino_, INPUT_PULLUP);
    }

    // Chame uma vez por volta do loop(), antes de perguntar qualquer coisa.
    void atualiza() {
        bool lido = (digitalRead(pino_) == LOW);
        unsigned long agora = millis();
        clique_ = false;

        switch (estado_) {
            case EstadoBotao::Solto:
                if (lido) {
                    estado_ = EstadoBotao::TalvezApertado;
                    desde_ms_ = agora;
                }
                break;

            case EstadoBotao::TalvezApertado:
                if (!lido) {
                    estado_ = EstadoBotao::Solto;          // era quique
                } else if (agora - desde_ms_ >= ESTAVEL_MS) {
                    estado_ = EstadoBotao::Apertado;       // firme: e clique
                    clique_ = true;
                }
                break;

            case EstadoBotao::Apertado:
                if (!lido) {
                    estado_ = EstadoBotao::TalvezSolto;
                    desde_ms_ = agora;
                }
                break;

            case EstadoBotao::TalvezSolto:
                if (lido) {
                    estado_ = EstadoBotao::Apertado;       // era quique
                } else if (agora - desde_ms_ >= ESTAVEL_MS) {
                    estado_ = EstadoBotao::Solto;
                }
                break;
        }
    }

    bool foi_apertado() const {
        return clique_;
    }

    bool esta_apertado() const {
        return estado_ == EstadoBotao::Apertado || estado_ == EstadoBotao::TalvezSolto;
    }
};

    O formato é o que a Lista 02 apresentou no exercício 4: atualiza() lê, uma vez por volta; as perguntas são const e podem ser feitas quantas vezes se quiser.

    O exemplo exemplos/cap04_debounce.cpp alimenta o botão com um aperto que quica na descida e na subida, lido a cada 5 ms:

    clique aceito em t=60 ms
bordas no sinal cru: 4
cliques do BotaoFiltrado: 1

    O sinal tinha 4 bordas; o BotaoFiltrado anunciou 1 clique, 30 ms depois de a leitura assentar.

    Esquemático de cap04-debounce: o mesmo circuito do capítulo 2. O que mudou foi só o código do botão.

    No Wokwi, o projeto wokwi/cap04-debounce/ é o contador do capítulo 2 com o BotaoFiltrado e sem "bounce": "0": o simulador está quicando o botão de propósito. Cinco apertos, cinco cliques.

    Por que 30 ms?

    Botões comuns quicam por alguns milissegundos. 30 ms é folgado para o quique e curto demais para alguém perceber atraso. Se um botão de verdade ainda contar cliques a mais, aumente; se parecer "lento", diminua. Esse é o tipo de número que fica numa constante com nome, e não espalhado pelo código.

    Juntando: semáforo com botão de pedestre¶

    Esquemático de cap04-semaforo: verde no GPIO 25, amarelo no 27, vermelho no 26, e o botão de pedestre no 32.

    O projeto wokwi/cap04-semaforo/ usa as duas máquinas ao mesmo tempo, com o botão quicando:

    #include "botao_filtrado.h"
#include "semaforo.h"

Semaforo semaforo(25, 27, 26);   // verde, amarelo, vermelho
BotaoFiltrado pedestre(32);
Fase ultima_fase = Fase::Verde;

void setup() {
    Serial.begin(115200);
    semaforo.inicia();
    pedestre.inicia();
    Serial.println("verde");
}

void loop() {
    pedestre.atualiza();
    if (pedestre.foi_apertado()) {
        semaforo.pede_travessia();
        Serial.println("  (pedestre pediu)");
    }

    semaforo.atualiza();

    // Imprime so quando a fase muda.
    if (semaforo.fase() != ultima_fase) {
        ultima_fase = semaforo.fase();
        Serial.println(nome_da_fase(ultima_fase));
    }
}

    nome_da_fase() é uma função livre em semaforo.h que converte cada Fase no texto correspondente, com um switch.

    Repare que o loop() é o do capítulo 3: uma lista de atualiza() e de perguntas rápidas. Duas máquinas de estados rodam lado a lado, cada uma no seu ritmo, e uma conversa com a outra por um evento (pede_travessia()). Esse formato aguenta muito mais do que parece. O projeto final de vários grupos vai ser exatamente isso, com mais máquinas.

    Padrão de projeto: máquina de estados e Debouncing

    O Semaforo é uma máquina de estados na forma mais direta: estados num enum class e regras num switch (no catálogo de Douglass, Single Event Receptor). O BotaoFiltrado é o padrão Debouncing, do mesmo catálogo.

    Há outras formas da mesma máquina: uma tabela de estados ou o padrão State, com uma classe por estado. O capítulo 16 compara as três e chega às máquinas hierárquicas, em que um estado contém outros. E o mesmo Semaforo vira um objeto ativo, que recebe eventos de outras tarefas.

    Erros comuns¶

    Esquecer o break num case. A execução "cai" no case seguinte e faz duas transições numa volta só. Compilando com -Wextra (como fazem o check.sh e o compilador online, se você ligar os avisos), o compilador acusa: this statement may fall through. Leia os avisos.

    fase_++ para ir à próxima fase. Não compila com enum class, e é bom que não compile: a ordem das fases é uma regra do sistema, e regra fica escrita no switch.

    Trocar de estado sem marcar o tempo. Se um case faz fase_ = Fase::Amarelo; sem atualizar entrou_ms_, o amarelo herda o tempo do verde e dura zero. Concentre a troca num método como entra().

    Perguntar foi_apertado() antes de atualiza(). A resposta é da volta anterior. A ordem no loop() é sempre: atualizar, depois perguntar.

    O pedido de pedestre "some". Ele foi registrado, mas apagado antes de ser atendido (por exemplo, zerando pedido_ no lugar errado). Pelo desenho, o pedido é atendido ao entrar no vermelho, e é só ali que ele é zerado.

    Resumo¶

    • Uma máquina de estados tem estados (um de cada vez), transições e os eventos ou condições que as disparam. Desenhe antes de programar.
    • Em C++: estados num enum class, regras num switch dentro de atualiza(), um case por estado.
    • Um único método (privado) troca de estado e faz tudo o que acompanha a troca.
    • Eventos externos só registram (pede_travessia()); a decisão fica no switch.
    • Debounce é uma máquina de estados: só um aperto que fica firme por um tempo vira clique.
    • Várias máquinas rodam juntas no mesmo loop(), desde que nenhuma espere.
