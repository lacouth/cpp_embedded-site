    2. Construtores, const e invariantes¶

    Vídeo

    Ainda não há vídeo para este capítulo.

    No capítulo 1, a classe Led funcionou. Neste capítulo ela fica difícil de usar errado. A ferramenta principal é o compilador: com duas palavras (explicit e const), erros que só apareceriam no Wokwi, depois de muito tempo procurando o fio solto, passam a ser recusados na compilação. O pretexto é uma peça nova: o botão.

    Invariante: o que tem que ser verdade sempre¶

    Um invariante é uma afirmação sobre o objeto que vale do nascimento à morte dele, não importa quais métodos sejam chamados. A Led do capítulo 1 tem dois:

    1. ligado_ diz a verdade sobre o pino: true se, e só se, o pino está em HIGH.
    2. pino_ nunca muda: um LED construído no 26 é o LED do 26 para sempre.

    O primeiro é protegido pelo private e pelos métodos: só liga() e desliga() escrevem no pino, e os dois atualizam o campo. O segundo, até agora, era protegido só pela boa vontade: nenhum método muda pino_, mas nada impede alguém de escrever um que mude. Já, já o compilador passa a cuidar disso.

    A peça nova: o botão¶

    O botão do curso fica entre um pino e o GND. Com o pino configurado como INPUT_PULLUP, um resistor dentro do chip puxa o pino para HIGH enquanto ninguém aperta. Apertar liga o pino ao GND:

    Botão digitalRead(pino)
    solto HIGH
    apertado LOW

    Está "ao contrário", e esse é o tipo de detalhe que uma classe deve esconder. Os detalhes elétricos estão na pinagem.

    A classe Botao¶

    class Botao {
private:
    const int pino_;     // const: o pino nunca muda depois de construido
    bool anterior_;      // o que esta_apertado() valia na ultima chamada

public:
    explicit Botao(int pino) : pino_(pino), anterior_(false) {}

    // Botao entre o pino e o GND: com o pull-up interno, solto le HIGH.
    void inicia() {
        pinMode(pino_, INPUT_PULLUP);
    }

    // Esconde a inversao do pull-up: true = o dedo esta no botao.
    bool esta_apertado() const {
        return digitalRead(pino_) == LOW;
    }

    // true so na volta em que o botao PASSA de solto para apertado.
    // Chame uma vez por volta do loop().
    bool foi_apertado() {
        bool agora = esta_apertado();
        bool borda = agora && !anterior_;
        anterior_ = agora;
        return borda;
    }
};

    São três palavras novas em relação à Led do capítulo 1: o explicit no construtor, o const no campo pino_ e a diferença entre o método const (esta_apertado) e o não-const (foi_apertado). Uma de cada vez.

    explicit: número não vira botão sozinho¶

    Imagine uma função que só olha para o botão:

    void relata(const Botao& b) {
    Serial.print("apertado? ");
    Serial.println(b.esta_apertado());
}

    Sem o explicit, um construtor que recebe um único int vira uma conversão automática de int para Botao. E esta chamada compila:

    relata(33);      // o programador queria passar o botao do pino 33...

    O compilador cria, em silêncio, um Botao temporário no pino 33, que nunca passou por inicia(), e o entrega para a função. O exemplo exemplos/cap02_sem_explicit.cpp faz exatamente isso:

    apertado? 0
apertado? 1

    A primeira linha é o botão de verdade, solto. A segunda é o temporário, num pino que ninguém configurou, dizendo que está apertado sem ninguém ter tocado nele. No Wokwi, a leitura de um pino solto pode ser qualquer coisa, e um bug desses consome uma tarde.

    Com explicit Botao(int pino), a conversão automática deixa de existir e a mesma linha é recusada:

    error: invalid initialization of reference of type 'const Botao&' from expression of type 'int'

    Regra prática

    Construtor que recebe um argumento leva explicit, a menos que você queira de propósito que aquele valor vire o objeto sozinho (o que, em classes de hardware, praticamente nunca acontece). A Led também ganha o seu: explicit Led(int pino).

    Campo const: o compilador protege o invariante¶

    const int pino_ transforma o invariante 2 em regra do compilador. Um método que tente trocar o pino não compila:

    void troca_pino(int novo) { pino_ = novo; }

    error: assignment of read-only member 'Botao::pino_'

    Há um preço: um campo const só pode receber valor na lista de inicialização do construtor (o trecho depois dos :), porque ela roda antes de o objeto existir de fato. Atribuir no corpo do construtor é tarde demais:

    explicit Botao(int pino) {
    pino_ = pino;
}

    error: uninitialized const member in 'const int' [-fpermissive]
error: assignment of read-only member 'Botao::pino_'

    É mais um motivo para o hábito que o C++ do Zero já recomendava: inicialize os campos sempre na lista de inicialização.

    Método const: quem só olha, e quem mexe¶

    esta_apertado() só lê o pino: não muda nenhum campo do objeto. Por isso leva const depois dos parênteses. Já foi_apertado() muda anterior_ a cada chamada, então não pode ser const.

    A diferença importa quando o objeto chega a uma função como referência const, como em relata(const Botao& b). Ali só métodos const podem ser chamados:

    void relata(const Botao& b) {
    if (b.foi_apertado()) {         // foi_apertado muda anterior_...
        Serial.println("clique");
    }
}

    error: passing 'const Botao' as 'this' argument discards qualifiers [-fpermissive]

    A mensagem é feia, mas diz exatamente isso: "você prometeu não mexer em b (const Botao&) e está chamando um método que mexe". Leia discards qualifiers como "jogaria fora o const".

    Borda: "está apertado" não é "foi apertado"¶

    Por que dois métodos de leitura? Porque o loop() roda milhares de vezes por segundo. Um dedo no botão por meio segundo são milhares de voltas com esta_apertado() == true. Se cada uma alternasse o LED, ele piscaria loucamente e terminaria num estado aleatório.

    O que se quer, quase sempre, é reagir ao instante em que o botão passa de solto para apertado: a borda de subida. Para isso, o objeto precisa lembrar como estava na volta anterior (o campo anterior_). O exemplo exemplos/cap02_borda.cpp simula seis voltas, com o dedo apertando, segurando e soltando:

    volta  esta_apertado  foi_apertado
  1          0              0
  2          1              1
  3          1              0
  4          1              0
  5          0              0
  6          1              1

    Três voltas seguidas com o botão apertado (2, 3 e 4) produzem um clique. O segundo clique só aparece na volta 6, depois que o botão foi solto na 5.

    Repare na ordem dentro de foi_apertado(): a borda é calculada antes de anterior_ ser atualizado. Invertendo as duas linhas, agora seria comparado consigo mesmo e a borda nunca apareceria.

    Botão e LED juntos¶

    Esquemático de cap02-botao-led: o botão liga o GPIO 32 ao GND quando apertado; não há resistor externo porque o pull-up é interno ao chip.

    O projeto wokwi/cap02-botao-led/ alterna o LED vermelho a cada clique no botão A e conta os cliques:

    #include "botao.h"
#include "led.h"

Botao botao_a(32);
Led vermelho(26);
int cliques = 0;

void setup() {
    Serial.begin(115200);
    botao_a.inicia();
    vermelho.inicia();
}

void loop() {
    if (botao_a.foi_apertado()) {
        cliques++;
        vermelho.alterna();
        Serial.print("clique ");
        Serial.println(cliques);
    }
}

    No Wokwi, clique no botão (ou aperte a tecla a do teclado, com a bancada selecionada): cada aperto imprime clique 1, clique 2, … e alterna o LED.

    O botão que quica¶

    Abra o diagram.json e procure o atributo "bounce": "0" do botão. Apague-o e rode de novo. Agora cada aperto produz vários cliques: num teste, cinco apertos viraram clique 76.

    Isso não é defeito do código, é física. Os contatos de metal de um botão de verdade batem e voltam algumas vezes antes de assentar (em inglês, bounce), e durante alguns milissegundos o pino oscila entre HIGH e LOW. Cada oscilação é uma borda legítima para foi_apertado(). O Wokwi simula esse quique por padrão, e o "bounce": "0" desliga a simulação.

    Na vida real não existe "bounce": "0". A solução, o debounce, precisa de duas ferramentas que ainda não temos: medir tempo sem travar o programa (capítulo 3) e uma máquina de estados (capítulo 4). Até lá, os exercícios usam "bounce": "0".

    Erros comuns¶

    O botão parece apertado o tempo todo, ou nunca. Faltou inicia(), então o pino ficou sem pull-up e lê o que quiser. Ou o fio está no contato errado: no Wokwi, um fio vai em 1.l/1.r e o outro em 2.l/2.r. Os dois no mesmo número estão sempre ligados entre si.

    esta_apertado() devolve o contrário. Comparar com HIGH em vez de LOW. Com INPUT_PULLUP, apertado é LOW.

    Um clique alterna o LED várias vezes. Ou você usou esta_apertado() onde deveria usar foi_apertado(), ou o botão está quicando (veja a seção anterior).

    foi_apertado() nunca devolve true. anterior_ foi atualizado antes de a borda ser calculada, ou foi_apertado() é chamado duas vezes na mesma volta (a primeira chamada "gasta" a borda).

    Resumo¶

    • Um invariante é o que precisa ser verdade sempre sobre o objeto. A classe existe para protegê-lo.
    • explicit em construtor de um argumento impede que um número vire objeto sem ninguém pedir.
    • Campo const faz o compilador garantir que ele nunca muda, e obriga a inicializá-lo na lista de inicialização.
    • Método const só lê. Por uma referência const, só métodos const podem ser chamados.
    • esta_apertado() é o estado agora; foi_apertado() é a borda, e precisa de memória (anterior_) entre as voltas.
    • Botões reais quicam. O Wokwi simula isso, e o conserto vem nos capítulos 3 e 4.
