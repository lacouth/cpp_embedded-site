    7. ADC e PWM atrás de um Adapter¶

    Vídeo

    Ainda não há vídeo para este capítulo.

    Um termômetro de ponteiro: um sensor de temperatura, um servo que aponta o valor numa escala e um buzzer que apita quando esquenta demais. Cada peça fala uma língua diferente. O sensor devolve um número de 0 a 4095, o servo quer a largura de um pulso em microssegundos e o buzzer quer uma frequência. Se a lógica do termômetro conversar com cada peça na língua dela, ela fica cheia de números que não têm nada a ver com temperatura.

    Este capítulo coloca um tradutor entre cada peça e o resto do programa: o padrão Adapter. O sensor passa a responder "25,1 °C, leitura válida", o servo passa a aceitar "vá para 68 graus", e trocar o sensor de temperatura por um potenciômetro vira uma mudança de duas linhas.

    ADC e PWM você já viu em Sistemas Microcontrolados

    Ler uma tensão com o conversor analógico-digital, controlar o brilho de um LED por PWM e mover um servo não são novidade. Este capítulo usa esses periféricos como cenário. O assunto é como organizar o código em volta deles: aritmética inteira, conversão de unidades, validação da leitura, e uma classe que esconde o periférico do resto do programa. Do hardware, só aparece o que é específico do ESP32 ou do core Arduino 3.x.

    O problema: números do hardware no meio da lógica¶

    A versão direta do termômetro funciona, e é assim que muito firmware começa:

    void loop() {
    int bruto = analogRead(35);
    float r = 10000.0 * bruto / (4095 - bruto);
    float c = 1 / (log(r / 10000) / 3950 + 1 / 298.15) - 273.15;
    ledcWrite(13, map(c, -20, 100, 446, 1966));
    if (c > 76) {
        ledcWriteTone(14, 880);
    } else {
        ledcWriteTone(14, 0);
    }
}

    Cada número desse loop() pertence a uma peça diferente: 4095 é o ADC, 10000 e 3950 são o NTC, 446 e 1966 são o servo. A lógica de verdade ("mostre a temperatura; apite acima de 76 °C") está enterrada no meio deles. E três perguntas ficam sem resposta boa:

    1. Trocar o sensor. Se o NTC virar outro sensor, quais linhas mudam? Todas as que tocam em bruto, r e c.
    2. Testar sem placa. Como conferir no computador que 2048 vira 25 °C, se a conta está misturada com ledcWrite?
    3. Sensor quebrado. Um fio solto produz alguma leitura. Quem decide que ela não presta?

    O ADC do ESP32, no que ele tem de diferente¶

    ESP32 com o core Arduino 3.x
    Resolução padrão 12 bits: analogRead devolve de 0 a 4095
    Atenuação padrão ADC_11db: a faixa de entrada vai até perto de 3,3 V. Escolha com analogSetPinAttenuation(pino, ADC_11db)
    Pinos do curso D34 (potenciômetro) e D35 (sensor): são do ADC1 e só entrada
    ADC2 os pinos do ADC2 (como 25, 26 e 27) não leem enquanto o Wi-Fi está ligado. Para não ter surpresa no capítulo 19, sensor analógico vai no ADC1

    O core oferece duas leituras: analogRead, o número bruto do conversor, e analogReadMilliVolts, que já devolve milivolts aplicando a curva de calibração gravada no chip. No Wokwi, com o potenciômetro em cinco posições, as duas deram isto:

    Posição do potenciômetro (0 a 1023) analogRead analogReadMilliVolts
    0 0 128
    256 1025 993
    512 2050 1858
    768 3074 2680
    1023 4095 3152

    No simulador, o conversor é ideal: o bruto cresce em linha reta, e 1,65 V (meio curso) vira 2050. O analogReadMilliVolts aplica a correção que um chip de verdade precisa, porque o ADC real do ESP32 entorta perto das pontas da faixa. Aplicada a um conversor que não entorta, a correção é que fica torta (1858 mV para 1,65 V). Por isso o curso usa o bruto, e a conversão para a unidade que interessa mora numa classe só. Se um dia a placa for real e precisar de calibração, é essa classe que muda.

    Aritmética inteira: escala() no lugar de map()¶

    Converter de uma faixa para outra é a conta mais comum de um Adapter: 0–4095 para 0–1000, 0–180 graus para 544–2400 µs. O Arduino tem map() para isso, mas ele tem dois defeitos: trunca a divisão e não satura fora da faixa. O curso usa uma função própria:

    // Leva x da faixa [de_min, de_max] para [para_min, para_max], arredondando
// para o inteiro mais proximo e saturando fora da faixa de entrada.
// (O map() do Arduino trunca e nao satura.) A conta e feita em 64 bits porque
// o produto do meio passa de 2^31 com facilidade.
constexpr int32_t escala(int32_t x, int32_t de_min, int32_t de_max,
                         int32_t para_min, int32_t para_max) {
    if (x <= de_min) {
        return para_min;
    }
    if (x >= de_max) {
        return para_max;
    }
    int64_t num = static_cast<int64_t>(x - de_min) * (para_max - para_min);
    int64_t den = de_max - de_min;
    int64_t meio = (num >= 0) ? den / 2 : -den / 2;
    return para_min + static_cast<int32_t>((num + meio) / den);
}

    Somar metade do denominador antes de dividir é o jeito inteiro de arredondar em vez de truncar. Lado a lado com o map() (exemplos/cap07_escala.cpp):

    ADC -> permil (0..4095 -> 0..1000)
  0: map 0  escala 0
  4: map 0  escala 1
  2047: map 499  escala 500
  2048: map 500  escala 500
  4095: map 1000  escala 1000
  4200: map 1025  escala 1000
permil -> graus, faixa invertida (0..1000 -> 180..0)
  0: map 180  escala 180
  333: map 121  escala 120
  500: map 90  escala 90
  1000: map 0  escala 0
produto do meio de escala(40000, 0, 65535, 0, 60000): 2400000000
maior int32_t:                                      2147483647
escala(40000, 0, 65535, 0, 60000) = 36622

    Três lições estão aí:

    • 4200 não existe num ADC de 12 bits, mas um bug ou um ruído pode produzi-lo. O map() devolve 1025 permil; a escala() segura em 1000.
    • 333 na faixa invertida: a conta exata dá 120,06. O map() responde 121, porque a divisão inteira do C++ trunca em direção ao zero, e com número negativo isso arredonda para cima.
    • O produto do meio passa de 2 bilhões com entradas modestas. Em int32_t, isso é transbordamento com sinal, comportamento indefinido. A conta em int64_t custa pouco e elimina o problema.

    E a função é constexpr: static_assert(escala(2048, 0, 4095, 0, 1000) == 500) é conferido pelo compilador, como as máscaras do capítulo 5.

    A unidade vai no nome

    O curso guarda grandezas em inteiros com a unidade no nome: permil (0 a 1000), decimos_c (251 = 25,1 °C), pulso_us. O ESP32 tem unidade de ponto flutuante para float, então não é por velocidade. É porque inteiro compara com == sem surpresa, cabe numa tabela, tem faixa conhecida, e o nome lembra a cada linha o que o número significa. Um float c não diz se está em graus, kelvin ou décimos.

    Do bruto à temperatura: tabela e interpolação¶

    O módulo NTC do Wokwi é um divisor de tensão: um resistor fixo de 10 kΩ entre 3,3 V e a saída, e um termistor NTC de 10 kΩ (a 25 °C) entre a saída e o GND. Esquentou, a resistência do NTC cai, e a leitura também. A relação exata usa a equação Beta, com logaritmo:

    R_ntc = 10 kΩ × bruto / (4095 − bruto)            (o divisor)
1/T   = 1/298,15 K + ln(R_ntc / 10 kΩ) / 3950      (a equação Beta, T em kelvin)

    Em vez de fazer essa conta a cada leitura, o firmware guarda uma tabela: a temperatura exata em alguns pontos, e uma reta entre eles. A tabela é gerada no computador, onde logaritmo não custa nada, por exemplos/cap07_tabela_ntc.cpp:

    // gerado por exemplos/cap07_tabela_ntc.cpp
    {3740,  -200},   //  -20 C
    {3495,  -100},   //  -10 C
    {3156,     0},   //    0 C
    {2738,   100},   //   10 C
    {2278,   200},   //   20 C
    {1825,   300},   //   30 C
    {1419,   400},   //   40 C
    {1081,   500},   //   50 C
    { 815,   600},   //   60 C
    { 613,   700},   //   70 C
    { 462,   800},   //   80 C
    { 350,   900},   //   90 C
    { 267,  1000},   //  100 C
pior erro da interpolacao: 0.52 C (leitura 3631, exato -15.08 C)
 -20 C: Wokwi 3740, equacao  3740.1, tabela -20.0 C
   0 C: Wokwi 3156, equacao  3156.2, tabela   0.0 C
  25 C: Wokwi 2048, equacao  2047.5, tabela  25.1 C
  50 C: Wokwi 1081, equacao  1081.4, tabela  50.0 C
  80 C: Wokwi  462, equacao   461.6, tabela  80.0 C
 100 C: Wokwi  267, equacao   267.0, tabela 100.0 C

    As linhas "Wokwi" são leituras medidas no simulador, com o NTC ajustado em cada temperatura: elas batem com a equação, o que confirma o modelo do módulo. E, entre todas as leituras possíveis, a reta erra no máximo 0,52 °C, no trecho mais curvo (perto de −15 °C). Com pontos a cada 5 °C, o erro cairia; é uma troca entre memória e precisão que se decide medindo.

    A interpolação só usa inteiros:

    // Interpolacao linear entre os dois pontos vizinhos, so com inteiros.
// Fora da tabela (frio demais, quente demais, fio solto ou em curto): invalida.
inline Leitura ntc_para_decimos(int32_t bruto) {
    for (int i = 0; i + 1 < PONTOS_NTC; i++) {
        const PontoNtc& a = TABELA_NTC[i];
        const PontoNtc& b = TABELA_NTC[i + 1];
        if (bruto <= a.bruto && bruto >= b.bruto) {
            int32_t num = (a.bruto - bruto) * (b.decimos_c - a.decimos_c);
            int32_t den = a.bruto - b.bruto;
            return {a.decimos_c + (num + den / 2) / den, true};
        }
    }
    return {0, false};
}

    O Adapter: um sensor que fala a língua do programa¶

    O que a função devolve não é só um número. É uma Leitura:

    // Um numero na unidade do sensor (permil, decimos de grau...) e se ele presta.
struct Leitura {
    int32_t valor;
    bool valida;    // false: fio solto, curto, ou fora da faixa que o sensor mede
};

    E cada sensor ganha uma classe que traduz o periférico para essa língua. O potenciômetro e o NTC são peças diferentes, mas as duas classes têm os mesmos métodos públicos:

    class Potenciometro {
private:
    const int pino_;

public:
    explicit Potenciometro(int pino) : pino_(pino) {}

    // 11 dB: a faixa do ADC vai ate perto de 3,3 V (e o padrao, mas dito aqui).
    void inicia() { analogSetPinAttenuation(pino_, ADC_11db); }

    // 0 = todo para a esquerda, 1000 = todo para a direita. Sempre valida.
    Leitura le() const { return {escala(analogRead(pino_), 0, 4095, 0, 1000), true}; }

    int32_t minimo() const { return 0; }
    int32_t maximo() const { return 1000; }
    const char* unidade() const { return "permil"; }
};

class SensorNtc {
private:
    const int pino_;

public:
    explicit SensorNtc(int pino) : pino_(pino) {}

    void inicia() { analogSetPinAttenuation(pino_, ADC_11db); }

    Leitura le() const { return ntc_para_decimos(analogRead(pino_)); }

    int32_t minimo() const { return TABELA_NTC[0].decimos_c; }
    int32_t maximo() const { return TABELA_NTC[PONTOS_NTC - 1].decimos_c; }
    const char* unidade() const { return "decimos de C"; }
};

    minimo() e maximo() dizem a faixa que o sensor mede, na unidade dele. Com eles, a lógica consegue posicionar um ponteiro ou decidir um limiar sem saber que sensor é. É isso que permite a troca da seção seguinte.

    No computador, com o Arduino falso, as mesmas classes respondem assim (exemplos/cap07_adapters.cpp; o teste põe a leitura no pino com falso::poe_analogico):

    atenuacao do 34 depois de inicia(): 3 (ADC_11db = 3)
pot: 501 permil, valida 1
ntc: 251 decimos de C, valida 1
ntc por leitura do ADC: 4095->invalida 3740->-200 3156->0 2048->251 462->800 267->1000 100->invalida 0->invalida

    Validar a faixa, e até onde isso vai¶

    Uma leitura fora da tabela é inválida: frio abaixo de −20 °C, calor acima de 100 °C, ou um defeito que leva a saída a um extremo (4095 ou 0). No Wokwi, com o controle do NTC no mínimo dele (−24 °C), o termômetro imprime leitura invalida, o buzzer fica quieto e o ponteiro fica onde estava. Um sensor quebrado não deve disparar um alarme, nem esconder um de verdade: o programa precisa saber que não sabe.

    Mas a validação por faixa tem limite, e o simulador mostra qual. Com o fio de sinal do NTC desconectado, o pino 35 fica flutuando e o ADC lê ruído. O Serial imprimiu, em segundos seguidos:

    154 decimos de C
194 decimos de C
115 decimos de C
305 decimos de C

    Todas são temperaturas plausíveis, dentro da faixa, e todas são lixo. Pegar esse defeito exige outro tipo de pergunta: "a temperatura pode subir 19 °C em um segundo?". É o padrão Smart Data do capítulo 18, sobre robustez. Por ora, guarde a lição: válido quer dizer dentro da faixa, e não necessariamente certo.

    Atuadores: o PWM do ESP32 no core 3.x¶

    O periférico de PWM do ESP32 se chama LEDC. No core Arduino 3.x, ele é usado por pino:

    Função O que faz
    ledcAttach(pino, freq_hz, bits) liga o PWM no pino, com essa frequência e essa resolução de duty
    ledcWrite(pino, duty) duty de 0 (sempre desligado) a 2bits − 1, que o core transforma em "sempre ligado"
    ledcWriteTone(pino, freq_hz) onda quadrada nessa frequência (para buzzer); 0 silencia

    Código antigo da internet usa outra API

    Até o core 2.x, o PWM era configurado por canal, com ledcSetup(canal, freq, bits) e ledcAttachPin(pino, canal). O core 3.x removeu essas funções. Se um exemplo copiado da internet não compila com 'ledcSetup' was not declared in this scope, é isso.

    Cada atuador ganha seu Adapter. Para o LED, o resto do programa fala em permil, como o potenciômetro:

    // Brilho de um LED (ou qualquer carga) em permil: 0 apagado, 1000 aceso.
class SaidaPwm {
private:
    const int pino_;
    const uint32_t freq_hz_;
    const uint8_t bits_;

public:
    SaidaPwm(int pino, uint32_t freq_hz, uint8_t bits)
        : pino_(pino), freq_hz_(freq_hz), bits_(bits) {}

    void inicia() { ledcAttach(pino_, freq_hz_, bits_); }

    void escreve_permil(int32_t permil) {
        int32_t maximo = (1 << bits_) - 1;
        ledcWrite(pino_, escala(permil, 0, 1000, 0, maximo));
    }
};

    O projeto wokwi/cap07-brilho/ liga o potenciômetro ao LED vermelho com esses dois Adapters, e o sketch.ino não tem nenhum 4095 nem nenhum duty:

    Potenciometro botao_giratorio(34);
SaidaPwm led_vermelho(26, 5000, 10);   // 5 kHz, 10 bits

void loop() {
    Leitura posicao = botao_giratorio.le();
    led_vermelho.escreve_permil(posicao.valor);
    // ... imprime quando muda
}

    No Wokwi, com o potenciômetro em três posições, o Serial e o brilho que o simulador desenha no LED foram estes:

    Potenciômetro Serial Brilho desenhado (0 a 1)
    0 0 permil 0
    256 250 permil 0,61
    1023 1000 permil 1

    Um quarto do duty aparece como bem mais que um quarto do brilho. O olho humano percebe brilho de forma não linear, e o simulador imita isso. Em produto de verdade, quem quer que "50%" pareça metade aplica uma correção (a "correção gama") dentro do Adapter, e o resto do programa nem fica sabendo.

    O servo¶

    Um servo de hobby recebe um pulso a cada 20 ms (50 Hz), e a largura do pulso diz o ângulo. No Wokwi, com o PWM de 14 bits a 50 Hz, a largura do pulso e o ângulo do servo foram:

    Pulso 500 µs 544 µs 1000 µs 1500 µs 2000 µs 2400 µs 2500 µs
    Ângulo no Wokwi 0° 0° 44° 93° 141° 180° 180°

    Uma reta de 544 µs (0°) a 2400 µs (180°), com batente nas pontas. São os mesmos extremos da biblioteca Servo do Arduino. Servos reais variam (500–2500 µs e 1000–2000 µs são comuns), e por isso os extremos são parâmetros do construtor: é a calibração do atuador, guardada no Adapter.

    class ServoMotor {
private:
    const int pino_;
    const int32_t pulso_min_us_;
    const int32_t pulso_max_us_;

    static const uint32_t FREQ_HZ = 50;      // periodo de 20 ms
    static const uint8_t BITS = 14;          // 20000 us viram 16384 passos
    static const int32_t PERIODO_US = 20000;

public:
    explicit ServoMotor(int pino, int32_t pulso_min_us = 544, int32_t pulso_max_us = 2400)
        : pino_(pino), pulso_min_us_(pulso_min_us), pulso_max_us_(pulso_max_us) {}

    void inicia() { ledcAttach(pino_, FREQ_HZ, BITS); }

    // 0 a 180 graus; fora disso, satura no batente.
    void vai_para(int32_t graus) {
        int32_t pulso_us = escala(graus, 0, 180, pulso_min_us_, pulso_max_us_);
        ledcWrite(pino_, escala(pulso_us, 0, PERIODO_US, 0, 1 << BITS));
    }
};

    São duas escalas encadeadas: graus para microssegundos, e microssegundos para passos do duty. O construtor tem três parâmetros, mas os dois últimos têm valor padrão. Então ServoMotor ponteiro(13); chama o construtor com um argumento, e por isso ele leva explicit.

    O buzzer¶

    O buzzer passivo precisa de uma onda quadrada na frequência do som. A classe só esconde o ledcWriteTone e lembra o que está tocando, para não reconfigurar o timer a cada volta do loop():

    class Buzzer {
private:
    const int pino_;
    uint32_t tocando_hz_;    // 0: em silencio

public:
    explicit Buzzer(int pino) : pino_(pino), tocando_hz_(0) {}

    void inicia() { ledcAttach(pino_, 1000, 10); silencia(); }

    void toca(uint32_t freq_hz) {
        if (freq_hz != tocando_hz_) {    // reconfigurar o timer a cada volta faria clique
            ledcWriteTone(pino_, freq_hz);
            tocando_hz_ = freq_hz;
        }
    }

    void silencia() { toca(0); }

    bool tocando() const { return tocando_hz_ != 0; }
};

    No computador, os três atuadores escrevem no PWM falso exatamente o que se espera:

    servo: 50 Hz, 14 bits
  -10 graus -> duty 446
  0 graus -> duty 446
  90 graus -> duty 1206
  180 graus -> duty 1966
  200 graus -> duty 1966
led 250 permil -> duty 256 de 1024
buzzer: 880 Hz, duty 511, tocando 1
buzzer silenciado: duty 0, tocando 0

    Os 446 e 1966 do loop() do começo do capítulo estão aí, mas agora são resultado de uma conta com nome, e não números mágicos.

    O termômetro de ponteiro¶

    O projeto wokwi/cap07-termometro/ junta tudo. Ele tem o potenciômetro e o NTC ligados ao mesmo tempo, para a troca da próxima seção não exigir mexer em fio:

    using Sensor = SensorNtc;        // ou: using Sensor = Potenciometro;
Sensor sensor(35);               //     Sensor sensor(34);
ServoMotor ponteiro(13);
Buzzer alarme(14);
Temporizador um_segundo(1000);

void setup() {
    Serial.begin(115200);
    sensor.inicia();
    ponteiro.inicia();
    alarme.inicia();
    um_segundo.reinicia();
    Serial.println("termometro de ponteiro");
}

void loop() {
    Leitura leitura = sensor.le();

    if (leitura.valida) {
        ponteiro.vai_para(escala(leitura.valor, sensor.minimo(), sensor.maximo(), 0, 180));
        int32_t limiar = sensor.minimo() + (sensor.maximo() - sensor.minimo()) * 8 / 10;
        if (leitura.valor >= limiar) {
            alarme.toca(880);
        } else {
            alarme.silencia();
        }
    } else {
        alarme.silencia();      // sensor quebrado nao e motivo para apitar
    }

    if (um_segundo.expirou()) {
        if (leitura.valida) {
            Serial.print(leitura.valor);
            Serial.print(" ");
            Serial.println(sensor.unidade());
        } else {
            Serial.println("leitura invalida");
        }
    }
}

    Compare com o loop() do começo do capítulo. Nenhum número dele pertence a uma peça. O ponteiro percorre a faixa do sensor de 0 a 180 graus, e o alarme dispara a 80% da faixa: com o NTC, 76 °C. No Wokwi, mexendo no controle do NTC (que vai de −24 °C a 80 °C):

    NTC em Serial Servo Buzzer
    25 °C 251 decimos de C 68° quieto
    79 °C 791 decimos de C 149° apitando
    −24 °C leitura invalida fica onde estava quieto

    A troca: o tipo numa linha¶

    As duas primeiras linhas do sketch usam um apelido de tipo: using Sensor = SensorNtc; diz que, neste arquivo, Sensor é outro nome para SensorNtc. Trocando essas duas linhas por

    using Sensor = Potenciometro;
Sensor sensor(34);

    e rodando de novo, com o potenciômetro no meio do curso, o Serial passa a mostrar 501 permil e o servo vai a 90°. Nada no loop() mudou, porque o loop() só usa o que as duas classes têm em comum: le(), minimo(), maximo() e unidade().

    Isso tem um limite, e ele é a porta do próximo capítulo. A troca acontece ao compilar: o programa escolhe um sensor e fica com ele. E se uma função tivesse que aceitar qualquer sensor, recebido como parâmetro, para um teste passar um sensor falso e a placa passar o NTC? Duas classes com os mesmos nomes de método não bastam para isso. É preciso dizer ao compilador que elas são o mesmo tipo de coisa. É o assunto do capítulo 8: interfaces, com virtual.

    Padrão de projeto: Adapter (Hardware Adapter) e sensor inteligente

    O Adapter (catálogo GoF) converte a interface que uma peça oferece na interface que o programa espera. Em firmware, Douglass chama de Hardware Adapter a classe que fica entre um periférico e a lógica: aqui, Potenciometro e SensorNtc transformam "0 a 4095" em "permil" e "décimos de grau", e ServoMotor transforma "graus" em "duty de 14 bits".

    Um Adapter de sensor que entrega a grandeza de engenharia, já calibrada, com a faixa e a validade junto, é o que a Instrumentação chama de sensor inteligente. A calibração (a tabela do NTC, os extremos do servo) mora no Adapter, e só nele.

    O Adapter volta no capítulo 17, na frente de displays diferentes. E a pergunta da última seção (aceitar qualquer sensor) é o capítulo 8.

    Erros comuns¶

    Ler o sensor num pino do ADC2 e funcionar até ligar o Wi-Fi. Os pinos do ADC2 param de ler quando o Wi-Fi está ativo. Sensor analógico vai nos pinos 32 a 39 (ADC1); o curso usa 34 e 35.

    map() com resultado fora da faixa. O map() não satura: uma leitura acima do esperado produz um ângulo acima de 180 ou um duty acima do máximo. Use escala(), ou satura antes de converter.

    Multiplicar antes de dividir em 32 bits. bruto * 3300 / 4095 cabe em int32_t; pulso * 16384 * 1000 não cabe. Quando o produto do meio pode passar de 2 bilhões, faça a conta em int64_t.

    Esquecer a unidade. int32_t temperatura = 251; são 251 graus ou 25,1? Ponha a unidade no nome (decimos_c) ou no tipo de retorno (Leitura com unidade()).

    Confiar em "válido". A validação por faixa pega curto e circuito aberto que levam a leitura a um extremo, mas não pega pino flutuando. Válido quer dizer plausível.

    Usar ledcSetup e ledcAttachPin. É a API do core 2.x, removida no 3.x. Use ledcAttach(pino, freq, bits) e ledcWrite(pino, duty).

    Chamar ledcWriteTone a cada volta do loop(). Ele reconfigura o timer do PWM. Lembre o que está tocando, como o Buzzer faz.

    Resumo¶

    • O ADC do ESP32 devolve 0 a 4095 (12 bits). No Wokwi ele é ideal; no chip real, entorta perto das pontas. A conversão para a unidade útil mora num Adapter.
    • escala() converte faixas com arredondamento, saturação e conta em 64 bits; o map() do Arduino trunca e não satura.
    • Grandezas em inteiros com a unidade no nome: permil, decimos_c, pulso_us.
    • O NTC vira temperatura por uma tabela gerada no computador e interpolação inteira; o pior erro, medido, é 0,52 °C.
    • Um sensor inteligente entrega Leitura (valor e validade), com a faixa (minimo(), maximo()) e a unidade. Válido não quer dizer certo.
    • O PWM do core 3.x é por pino: ledcAttach, ledcWrite, ledcWriteTone. Servo é PWM de 50 Hz com pulso de 544 a 2400 µs no Wokwi.
    • Classes com os mesmos métodos se trocam pelo tipo (using Sensor = ...), ao compilar. Para trocar em tempo de execução, ou num teste, o capítulo 8 traz interfaces.
