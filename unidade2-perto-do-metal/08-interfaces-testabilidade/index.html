    8. Interfaces, HAL e padrões de testabilidade¶

    Vídeo

    Ainda não há vídeo para este capítulo.

    Duas aulas

    Este capítulo ocupa duas aulas. A Parte 1 (interfaces sem heap, injeção de dependência, o tempo como dependência) é a primeira; a Parte 2 (dublês de teste, seams, escrever o teste antes) é a segunda.

    O capítulo 7 terminou com uma pergunta. O Potenciometro e o SensorNtc têm os mesmos métodos, e o termômetro troca um pelo outro mudando o tipo numa linha. Mas a troca acontece ao compilar: o programa escolhe um sensor e fica com ele. E se uma classe tivesse que aceitar qualquer sensor, recebido no construtor, para que um teste no computador passe um sensor falso e a placa passe o de verdade?

    A resposta já apareceu no C++ do Zero: uma interface, com virtual. Este capítulo revê a ideia depressa e vai além do que lá foi visto: interface sem heap, o tempo como dependência, os quatro tipos de dublê de teste, e o que significa escrever o teste antes do código.

    O problema: a bomba que só se testa esperando¶

    Uma caixa d'água com uma bomba. A bomba liga quando o nível cai a 500 mm e desliga quando chega a 1800 mm. E há uma regra de segurança: se a bomba ficar ligada dez minutos sem encher a caixa, alguma coisa está errada (o poço secou, o cano furou) e ela precisa desligar e acender um alarme, até alguém conferir e rearmar.

    Escrita do jeito direto:

    void loop() {
    int bruto = analogRead(34);
    int mm = (bruto - 410) * 2000 / 3280;
    if (!ligada && mm <= 500) {
        digitalWrite(4, HIGH);
        ligada = true;
        ligou_em = millis();
    } else if (ligada && mm >= 1800) {
        digitalWrite(4, LOW);
        ligada = false;
    } else if (ligada && millis() - ligou_em >= 600000) {
        digitalWrite(4, LOW);
        digitalWrite(26, HIGH);
        bloqueada = true;
    }
}

    Como testar a regra dos dez minutos? Do único jeito que este código permite: ligar tudo, deixar o nível baixo, e esperar dez minutos olhando um LED. E depois, a cada mudança no código, esperar de novo. A lógica depende de três coisas que só existem na placa: analogRead, digitalWrite e millis(). O arduino_falso.h resolve parte disso trocando o #include, mas o relógio continua sendo uma variável global escondida, e o teste não tem como dizer "agora são 9 minutos e 59 segundos".

    Parte 1 · Interfaces sem heap¶

    Revisão: virtual, override e classe abstrata¶

    Se você fez o C++ do Zero, isto é revisão dos capítulos 11 e 15. Se não fez, é o mínimo para seguir.

    Uma classe filha pode ter um método com o mesmo nome do da classe base. Quem decide qual dos dois roda numa chamada por referência à base é a palavra virtual (exemplos/cap08_ligacao.cpp):

    class ISaida {
public:
    virtual ~ISaida() = default;
    virtual void liga() = 0;
};

class Led : public ISaida {
public:
    void liga() override { std::cout << "  Led::liga (escreve HIGH)\n"; }
};

class Rele : public ISaida {
public:
    void liga() override { std::cout << "  Rele::liga (escreve LOW)\n"; }
};

void aciona(ISaida& s) { s.liga(); }

    O mesmo programa tem uma versão sem virtual (SaidaSemVirtual e ReleSemVirtual). A saída:

    sem virtual, um rele por referencia a base:
  SaidaSemVirtual::liga (nao sabe que pino)
com virtual:
  Led::liga (escreve HIGH)
  Rele::liga (escreve LOW)

    Sem virtual, o compilador decide pelo tipo da referência, e o relé nunca é acionado como relé. Com virtual, decide em tempo de execução pelo objeto de verdade. Três detalhes completam a revisão:

    • = 0 faz do método um virtual puro. Uma classe com um método assim é abstrata: não dá para criar um objeto dela, só das filhas que implementam tudo. É isso que se chama de interface em C++.
    • override é opcional, mas pede ao compilador para conferir que o método realmente substitui um da base. Um nome digitado errado (void lig() override) vira erro de compilação, em vez de um método novo que ninguém chama.
    • virtual ~ISaida() = default;: toda classe pensada para ser usada por referência à base tem destrutor virtual. Neste curso nenhum objeto é destruído pela base (não há delete), mas a regra é barata e evita o dia em que alguém usar um.

    O preço: um ponteiro por objeto¶

    Para decidir em tempo de execução, cada objeto de uma classe com métodos virtuais carrega um ponteiro escondido para a tabela de métodos virtuais da sua classe. No ESP32 do Wokwi, a mesma saída digital, com e sem virtual:

    Classe sizeof no ESP32
    void* (um ponteiro) 4
    SaidaSemVirtual (pino, polaridade, estado) 8
    SaidaDigital (os mesmos campos, herdando de ISaida) 12

    Quatro bytes a mais por objeto: o ponteiro. A tabela em si é uma só por classe, e não uma por objeto. Além da memória, cada chamada virtual passa pela tabela antes de pular para o método. Quanto tempo isso custa, e a alternativa sem custo (templates), é a segunda aula do capítulo 11, com números medidos.

    As três interfaces do curso¶

    O esqueleto do projeto (projetos/esqueleto/logica/interfaces.h) define as três que a disciplina vai usar até o fim:

    // Um sensor que entrega a grandeza ja convertida, com a faixa e a validade
// (o sensor inteligente do capitulo 7).
class ISensor {
public:
    virtual ~ISensor() = default;
    virtual Leitura le() const = 0;
    virtual int32_t minimo() const = 0;
    virtual int32_t maximo() const = 0;
    virtual const char* unidade() const = 0;
};

// Uma saida de dois estados: LED, rele, sirene.
class ISaida {
public:
    virtual ~ISaida() = default;
    virtual void liga() = 0;
    virtual void desliga() = 0;
    virtual bool ligada() const = 0;
};

// A hora, em milissegundos. Na placa e o millis(); no teste, um relogio que
// so anda quando o teste manda.
class IRelogio {
public:
    virtual ~IRelogio() = default;
    virtual uint32_t agora_ms() const = 0;
};

    O ISensor é exatamente o que o Potenciometro e o SensorNtc do capítulo 7 já faziam, agora com nome. E o arquivo não inclui <Arduino.h>: quem depende só destas interfaces compila em qualquer lugar.

    O tempo também é uma dependência¶

    O IRelogio é a peça que o C++ do Zero não tinha, e a que resolve o problema dos dez minutos. Uma classe que chama millis() depende de um relógio global, que ela mesma vai buscar. Uma classe que recebe um IRelogio& depende de um relógio, que alguém lhe entregou. Na placa, esse alguém entrega o millis():

    class RelogioArduino : public IRelogio {
public:
    uint32_t agora_ms() const override { return static_cast<uint32_t>(millis()); }
};

    No teste, entrega um relógio que só anda quando o teste manda. E aí "dez minutos depois" é uma linha.

    A ControleBomba¶

    A lógica da bomba é uma máquina de estados (capítulo 4) que só conhece interfaces:

    class ControleBomba {
public:
    enum class Estado { Parada, Bombeando, Bloqueada };

    struct Config {
        int32_t liga_abaixo;
        int32_t desliga_acima;
        uint32_t tempo_max_ms;
    };

private:
    const ISensor& nivel_;
    ISaida& bomba_;
    ISaida& alarme_;
    const IRelogio& relogio_;
    const Config config_;
    Estado estado_;
    uint32_t ligou_em_ms_;

public:
    ControleBomba(const ISensor& nivel, ISaida& bomba, ISaida& alarme,
                  const IRelogio& relogio, Config config)
        : nivel_(nivel), bomba_(bomba), alarme_(alarme), relogio_(relogio),
          config_(config), estado_(Estado::Parada), ligou_em_ms_(0) {}

    // Chame a cada volta do loop().
    void atualiza() {
        Leitura nivel = nivel_.le();
        uint32_t agora = relogio_.agora_ms();

        switch (estado_) {
        case Estado::Parada:
            if (nivel.valida && nivel.valor <= config_.liga_abaixo) {
                bomba_.liga();
                ligou_em_ms_ = agora;
                estado_ = Estado::Bombeando;
            }
            break;
        case Estado::Bombeando:
            if (!nivel.valida || nivel.valor >= config_.desliga_acima) {
                bomba_.desliga();
                estado_ = Estado::Parada;
            } else if (agora - ligou_em_ms_ >= config_.tempo_max_ms) {
                bomba_.desliga();
                alarme_.liga();
                estado_ = Estado::Bloqueada;
            }
            break;
        case Estado::Bloqueada:
            break;      // so rearma() tira daqui
        }
    }

    // O operador conferiu a bomba e mandou tentar de novo.
    void rearma() {
        if (estado_ == Estado::Bloqueada) {
            alarme_.desliga();
            estado_ = Estado::Parada;
        }
    }

    Estado estado() const { return estado_; }
};

    Ela recebe tudo de que precisa pelo construtor: é a injeção de dependência. A classe não sabe se o sensor é um potenciômetro, uma boia ou um teste, nem se a bomba é um relé ou um LED. Note também a segurança: leitura inválida com a bomba ligada desliga a bomba (a lição do capítulo 7: um sensor quebrado não pode deixar o motor ligado).

    Sem heap: referências, e quem é dono¶

    No C++ do Zero, objetos polimórficos costumavam nascer com new ou std::make_unique e viver num std::vector. Num firmware do curso, nada é alocado depois do setup(). A ControleBomba guarda referências, e os objetos de verdade são variáveis globais, criados antes do setup() e vivos até a placa desligar:

    SensorNivel nivel(34);          // potenciometro no papel de sensor de nivel
SaidaDigital bomba(4);          // modulo rele, ativo em nivel alto
SaidaDigital alarme(26);        // LED vermelho
RelogioArduino relogio;
BotaoFiltrado rearme(32);       // botao A
ControleBomba controle(nivel, bomba, alarme, relogio, {500, 1800, 15000});

    Esse bloco é a raiz de composição: o único lugar do programa que sabe quais peças estão na bancada. Mudar o hardware é mudar estas linhas; a lógica não é tocada. E ele resolve de graça a pergunta "quem é dono de quem": ninguém é dono de ninguém, todos vivem o programa inteiro, e uma referência nunca fica apontando para um objeto que já morreu. Ou seja, o objeto referenciado precisa viver pelo menos tanto quanto quem o referencia. Variáveis globais cumprem isso sempre.

    Na placa¶

    Do lado do hardware, cada interface ganha uma implementação. A SaidaDigital serve ao LED e ao relé, porque os dois são "um pino que liga e desliga":

    class SaidaDigital : public ISaida {
private:
    const int pino_;
    const bool ativo_alto_;     // false: liga com LOW (muitos modulos rele sao assim)
    bool ligada_;

public:
    explicit SaidaDigital(int pino, bool ativo_alto = true)
        : pino_(pino), ativo_alto_(ativo_alto), ligada_(false) {}

    void inicia() {
        pinMode(pino_, OUTPUT);
        desliga();
    }

    void liga() override {
        digitalWrite(pino_, ativo_alto_ ? HIGH : LOW);
        ligada_ = true;
    }

    void desliga() override {
        digitalWrite(pino_, ativo_alto_ ? LOW : HIGH);
        ligada_ = false;
    }

    bool ligada() const override { return ligada_; }
};

    O inicia() não está na interface: configurar o pino é assunto de quem monta a bancada, no setup(), e não da lógica. A ControleBomba nunca chama inicia().

    O projeto wokwi/cap08-bomba/ (o mesmo código de projetos/esqueleto/wokwi/) usa o potenciômetro como sensor de nível, um módulo relé no pino 4 com um LED verde como carga ("a bomba"), o LED vermelho como alarme e o botão A para rearmar. Para a demonstração, o tempo máximo é 15 segundos em vez de dez minutos:

    O relé do Wokwi é ativo em nível alto

    No módulo relé do Wokwi (com o padrão "transistor": "npn"), o pino IN em HIGH fecha o contato COM–NO. Isso foi conferido no simulador; o texto da documentação da peça descreve o contrário. Muitos módulos reais são ativos em nível baixo: é para eles o segundo parâmetro da SaidaDigital.

    No Wokwi:

    O que fizemos Serial LEDs
    Potenciômetro em 150 (116 mm) -> bombeando verde (bomba) aceso
    Esperamos 15 s com o nível baixo -> BLOQUEADA verde apaga, vermelho acende
    Apertamos o botão A -> bombeando vermelho apaga, verde acende
    Subimos o potenciômetro até 1957 mm -> parada os dois apagados

    Depois do rearme, o Serial mostra -> bombeando direto, sem -> parada: o rearma() leva a máquina para Parada, e o atualiza() da mesma volta do loop() vê o nível baixo e liga de novo. O sketch só imprime o estado do fim da volta.

    Parte 2 · Padrões de testabilidade¶

    Dublês de teste¶

    No cinema, o dublê substitui o ator nas cenas em que o ator não pode estar. No teste, um dublê substitui uma dependência que o teste não pode (ou não quer) usar de verdade. O nome e a classificação são de Gerard Meszaros, e cada tipo faz uma coisa:

    Dublê O que faz No curso
    Stub devolve o que o teste programou, sem lógica nenhuma SensorProgramado: o teste diz "o nível é 400"
    Fake funciona de verdade, mas de um jeito que não serve para produção RelogioFalso: um relógio que só anda com avanca(); e o arduino_falso.h desde o capítulo 1
    Spy funciona e anota o que lhe fizeram, para o teste conferir depois SaidaEspia: guarda cada liga e desliga, com a hora
    Mock sabe de antemão o que deveria acontecer e confere a cada chamada SaidaMock: "espero um liga e depois um desliga, e nada mais"

    Os quatro estão em projetos/esqueleto/host/duplos.h, sem heap (o espião guarda os eventos num array de 16 posições). O stub e o fake são curtos:

    // STUB: devolve o que o teste programou. Nao tem logica nenhuma.
class SensorProgramado : public ISensor {
private:
    Leitura leitura_;
    int32_t minimo_;
    int32_t maximo_;

public:
    SensorProgramado(int32_t minimo, int32_t maximo)
        : leitura_{0, true}, minimo_(minimo), maximo_(maximo) {}

    void poe(int32_t valor) { leitura_ = {valor, true}; }
    void poe_invalida() { leitura_ = {0, false}; }

    Leitura le() const override { return leitura_; }
    int32_t minimo() const override { return minimo_; }
    int32_t maximo() const override { return maximo_; }
    const char* unidade() const override { return "mm"; }
};

// FAKE: um relogio que funciona de verdade, mas so anda quando o teste manda.
class RelogioFalso : public IRelogio {
private:
    uint32_t agora_ms_;

public:
    RelogioFalso() : agora_ms_(0) {}

    void avanca(uint32_t ms) { agora_ms_ += ms; }
    uint32_t agora_ms() const override { return agora_ms_; }
};

    Dez minutos em zero segundo¶

    Com os dublês, a regra dos dez minutos se testa assim (exemplos/cap08_bomba_no_host.cpp): o sensor programado diz "400 mm", e o relógio falso anda um segundo por volta, por 700 voltas:

    SensorProgramado nivel(0, 2000);    // stub
RelogioFalso relogio;               // fake
SaidaEspia bomba(relogio);          // spy
SaidaEspia alarme(relogio);         // spy
ControleBomba controle(nivel, bomba, alarme, relogio, {500, 1800, 10u * 60 * 1000});

nivel.poe(400);                     // caixa baixa
for (int segundo = 0; segundo <= 700; segundo++) {   // 11 min 40 s, um segundo por volta
    controle.atualiza();
    relogio.avanca(1000);
}

    Os espiões contam o que aconteceu, com a hora:

    bomba : liga@0s desliga@600s
alarme: liga@600s
alarme: liga@600s desliga@701s
estado final: parada

    A bomba ligou no segundo 0 e desistiu no 600, exatamente aos dez minutos; o alarme acendeu no mesmo instante e apagou com o rearme. O programa inteiro roda em milissegundos. Os testes do esqueleto (projetos/esqueleto/host/teste_controle_bomba.cpp) vão mais fundo: conferem o comportamento em 9 min 59,999 s e em 10 min exatos, a histerese, o sensor quebrado com a bomba parada e com a bomba ligada.

    O que o espião não vê e o mock vê¶

    O espião e o mock parecem fazer a mesma coisa, mas perguntam coisas diferentes. Uma versão com bug da bomba, que chama liga() em toda volta em que o nível está baixo, mesmo com a bomba já ligada (exemplos/cap08_mock.cpp):

    espiao: ligada = 1, chamadas anotadas = 3
mock: conferiu = 0, recebidas = 3, primeiro erro na chamada 1

    O espião anotou as três chamadas, mas um teste que só pergunta "a bomba está ligada?" passa: está. O bug só aparece se o teste lembrar de contar as chamadas. O mock foi programado com a expectativa ("um liga, e nada mais") e acusa sozinho, já na segunda chamada (a de índice 1). Num relé, ligar o que já está ligado não muda o pino; mas se a "saída" fosse um comando pela rede, uma contagem de partidas do motor ou um log de auditoria, a chamada repetida seria o bug.

    A regra prática: espião quando importa o estado no fim; mock quando importa a sequência exata de chamadas. E, nos dois casos, quanto mais o teste depende de como a classe faz as coisas (e não do que ela produz), mais ele quebra quando alguém melhora a implementação.

    Seams: onde se troca o real pelo dublê¶

    Michael Feathers chama de seam (costura) o lugar onde dá para trocar o comportamento de um programa sem editar o código que se quer testar. O curso já usou dois:

    Link seam Interface seam
    Como troca outro arquivo no lugar: "arduino_falso.h" no computador, <Arduino.h> na placa outro objeto no construtor: SensorProgramado no teste, SensorNivel na placa
    Desde capítulo 1 este capítulo
    Custa nada em tempo de execução um ponteiro por objeto e uma chamada indireta
    Troca tudo de uma vez, para o programa inteiro cada dependência, de cada objeto, separadamente
    Bom para código que já chama digitalWrite direto, sem mudar nada lógica nova, e testes que precisam de vários dublês diferentes

    James Grenning, que trouxe o desenvolvimento guiado por testes para o firmware em C, usa os dois: link seam para o código de baixo nível que já existe, interface seam para a lógica. O curso faz o mesmo.

    Escrever o teste antes¶

    Um pedido novo: depois de desligar, a bomba precisa descansar pelo menos 60 segundos antes de partir de novo, porque partidas seguidas esquentam o motor. Antes de mexer na classe, escreve-se o teste: encher a caixa, esvaziar logo em seguida, e conferir quando a bomba religou. Rodado contra a classe de hoje, ele precisa falhar; só então se escreve o código que o faz passar (exemplos/cap08_tdd.cpp):

    versao de hoje:  religou em 31 s -> FALHOU (descanso minimo e 60 s)
versao nova:     religou em 90 s -> passou

    O vermelho antes do verde não é burocracia: um teste que nunca falhou pode estar testando nada (um assert que sempre passa, uma condição invertida). Vê-lo falhar pelo motivo certo prova que ele detecta a ausência da funcionalidade. É o ciclo do Test-Driven Development: vermelho (o teste falha), verde (o mínimo de código para passar), refatorar (limpar com os testes como rede de proteção).

    A pasta wokwi/ tem uma cópia dos arquivos de logica/ porque o Wokwi quer todos os arquivos do projeto juntos, em abas. A regra é editar em logica/ e copiar; no repositório do curso, uma verificação confere que as cópias estão iguais.

    Padrão de projeto: interface, injeção de dependência e HAL

    Uma interface (classe abstrata) separa o que uma peça faz de como ela faz. A injeção de dependência entrega a cada objeto, pelo construtor, as peças de que ele precisa, em vez de ele mesmo ir buscá-las (millis(), um pino fixo). O conjunto das interfaces que isolam a lógica do hardware (ISensor, ISaida, IRelogio) é uma pequena HAL (Hardware Abstraction Layer, camada de abstração de hardware). E a raiz de composição, no sketch.ino, é o único lugar que conhece as peças de verdade.

    Padrões de projeto: dublês de teste e seams

    Stub, Fake, Spy e Mock (Meszaros, xUnit Test Patterns) são quatro jeitos de substituir uma dependência num teste, de "devolve o que eu mandar" até "confere cada chamada". Um seam (Feathers) é o ponto onde a troca acontece: no arquivo que se inclui (link seam) ou no objeto que se injeta (interface seam). Grenning aplica os dois em firmware.

    Os dublês voltam em todo capítulo daqui em diante: a fila do capítulo 14, o mutex do 15 e o watchdog do 18 são testados no computador com eles.

    Erros comuns¶

    Esquecer o virtual. O código compila, mas a chamada por referência à base executa o método da base. O sintoma é "o meu liga() nunca é chamado". Use override nas filhas: sem virtual na base, o override vira erro de compilação.

    Errar a assinatura na filha. void liga() const override numa base que tem void liga() não substitui nada. Com override, o compilador avisa; sem ele, nasce um método novo que ninguém chama.

    Referência para um temporário. ControleBomba controle(SensorNivel(34), bomba, alarme, relogio, cfg); compila: o SensorNivel(34) é criado, a referência guarda o endereço dele, e ele é destruído no fim da linha. A classe passa a ler um objeto morto. Os objetos referenciados precisam ser variáveis com vida longa (no curso, globais).

    Tentar criar um objeto da interface. ISaida saida; não compila: a classe é abstrata. Crie um objeto de uma implementação (SaidaDigital) e passe-o como ISaida&.

    Chamar millis() dentro da lógica. Aí o teste volta a precisar esperar. Toda leitura de tempo na lógica passa por um IRelogio&.

    Testar com o dublê errado. Um teste que só pergunta ligada() não pega chamadas repetidas; um mock que exige a sequência exata quebra quando alguém reorganiza a classe sem mudar o resultado. Escolha pelo que importa: o estado final ou a sequência.

    Pôr inicia() na interface. Configurar o pino é trabalho da raiz de composição, no setup(). Se a interface tem inicia(), todo dublê precisa implementá-lo, e a lógica fica tentada a chamá-lo.

    Resumo¶

    • Interface em C++ é uma classe abstrata (métodos virtual ... = 0), com destrutor virtual; as filhas usam override. Sem virtual, a chamada pela base executa a base.
    • virtual custa um ponteiro por objeto: no ESP32, a SaidaDigital vai de 8 para 12 bytes.
    • O curso usa três interfaces: ISensor, ISaida e IRelogio. O tempo é uma dependência como as outras.
    • Injeção de dependência pelo construtor, com referências e objetos globais: sem heap, e sem dúvida sobre quem vive mais.
    • A raiz de composição (os objetos globais do sketch.ino) é o único lugar que conhece o hardware.
    • Dublês: Stub (devolve o programado), Fake (funciona, mas simplificado), Spy (anota), Mock (confere a expectativa). Espião para o estado final, mock para a sequência.
    • Link seam troca um arquivo; interface seam troca um objeto.
    • Escreva o teste antes e veja-o falhar: um teste que nunca falhou não provou nada.
    • projetos/esqueleto/ (lógica, testes no computador e Wokwi) é o ponto de partida do projeto final.
