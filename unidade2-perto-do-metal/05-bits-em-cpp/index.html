    5. Bits em C++ e registradores tipados¶

    Vídeo

    Ainda não há vídeo para este capítulo.

    Todo periférico do ESP32 (os pinos, os timers, o PWM, o I2C) é comandado escrevendo e lendo bits em registradores. Em Circuitos Lógicos e em Arquitetura de Computadores você já fez as contas que isso exige: binário, hexadecimal, complemento de dois, máscaras. Este capítulo usa essas contas sem refazê-las, e se concentra no lado C++: que tipo usar para guardar 32 bits sem surpresa, como escrever uma máscara que o compilador confere, e como esconder um registrador atrás de uma classe que dá nome a cada campo. É a base do capítulo 6, quando o registrador deixa de ser uma variável e passa a ser um endereço do ESP32.

    Tudo aqui roda no computador. O registrador é uma variável uint32_t comum, que faz o papel do de verdade.

    As contas estão enferrujadas?

    Se você não lembra bem como se lê 0x2F em binário, por que −5 em 8 bits é 1111'1011, ou o que sobra de 1100'1010 & 0000'1111, passe antes pela Revisão: binário, hexadecimal e operações com bits. Ela refaz o caminho em passos pequenos, com exercícios e respostas, e leva uns 30 minutos. O capítulo fica muito mais leve depois dela.

    O problema: um número que é, na verdade, 32 interruptores¶

    No ESP32, ligar o pino 26 por registrador é escrever 1 no bit 26 de uma palavra de 32 bits. Configurar um timer é gravar um divisor de 8 bits numa faixa da palavra, ligar um bit de "conta" em outra, escolher o modo em mais dois. Para o hardware, a palavra é um painel de interruptores: cada bit (ou grupo de bits) controla uma coisa diferente.

    Para o C++, é um número. E aí moram três perigos:

    1. O tamanho errado. Se o tipo não tiver exatamente 32 bits, as contas de deslocamento mudam de significado.
    2. Mexer em tudo para mudar uma coisa. reg = 1u << 3 liga o bit 3 e desliga todos os outros.
    3. Números mágicos. reg |= 0x500B está certo ou errado? Ninguém sabe sem abrir o manual.

    O capítulo resolve um de cada vez.

    Tipos de tamanho fixo¶

    int, long e companhia têm o tamanho que a plataforma escolher. O exemplos/cap05_tamanhos.cpp pergunta ao compilador do computador (Linux, 64 bits):

    char      1
short     2
int       4
long      8
long long 8
uint8_t   1
uint16_t  2
uint32_t  4
uint64_t  8

    O mesmo sizeof, rodando no ESP32 do Wokwi:

    int       4
long      4
long long 8
uint32_t  4

    O long tem 8 bytes num e 4 no outro. (No Arduino Uno, com processador AVR, até o int muda: 2 bytes.) Código que assume o tamanho de long funciona num lugar e quebra no outro. É por isso que o millis() do capítulo 3 devolve unsigned long, que no ESP32 tem 32 bits e dá a volta em uns 49 dias.

    A solução é o cabeçalho <cstdint>, que define tipos com o tamanho no nome:

    Tipo Bits Faixa Uso típico
    uint8_t 8 0 a 255 um byte vindo de um sensor, um componente de cor
    uint16_t 16 0 a 65 535 leitura de ADC, pixel RGB565
    uint32_t 32 0 a 4 294 967 295 registrador do ESP32
    int16_t 16 −32 768 a 32 767 eixo de um acelerômetro (capítulo 17)

    Duas regras práticas:

    • Registrador é sempre uint32_t: tem 32 bits em qualquer plataforma e é sem sinal, então deslocar para a direita sempre traz zeros, e "dar a volta" é comportamento definido.
    • uint8_t não é letra, mas o std::cout acha que é. No computador, std::cout << d com uint8_t d = 80 imprime P (o caractere de código 80). Escreva +d (ou converta para int) para ver o número. O Serial.println do Arduino imprime 80, sem esse susto.

    As quatro operações, em C++¶

    As contas você conhece (se não, as tabelas das operações e a ideia de "E apaga, OU acende, OU-exclusivo inverte" estão na revisão). O que importa aqui é a forma de escrevê-las para mexer num bit sem tocar nos outros:

    Quero Escrevo Por quê
    ligar o bit n reg |= (1u << n); OU com 1 liga; OU com 0 não muda nada
    desligar o bit n reg &= ~(1u << n); E com 0 desliga; E com 1 não muda nada
    inverter o bit n reg ^= (1u << n); OU-exclusivo com 1 inverte
    testar o bit n (reg >> n) & 1u traz o bit para a posição 0 e isola

    Repare no 1u: o u faz a constante ser unsigned. Com o 1 puro (que é int, com sinal), deslocar até o bit 31 dá um número negativo, e as comparações seguintes ficam estranhas.

    Em exemplos/cap05_bits.cpp, um "registrador" de 8 bits passa pelas quatro operações (o binario() do exemplo só imprime os bits em grupos de 4):

    uint32_t reg = 0b0000'0101;
reg |= (1u << 7);                         // liga o bit 7
reg &= ~(1u << 0);                        // desliga o bit 0
reg ^= (1u << 2);                         // inverte o bit 2
bool ligado = (reg >> 7) & 1u;            // testa o bit 7
reg = 1u << 3;                            // ERRO comum: = no lugar de |=

    inicio        0000 0101
liga 7        1000 0101
desliga 0     1000 0100
inverte 2     1000 0000
bit 7 ligado? 1
reg = 1u << 3 0000 1000

    A última linha é o perigo 2: com =, o bit 3 foi ligado e o bit 7, que estava ligado, sumiu.

    Dois detalhes de escrita do C++14 que ajudam a ler registradores:

    • literal binário 0b0000'0101, além do hexadecimal 0x05;
    • separador de dígitos ': 0x0000'0301 e 0b1000'0101 se leem em grupos, como o manual mostra.

    Campos de vários bits¶

    Muitos registradores guardam campos: um número de vários bits numa faixa da palavra. O registrador de controle de um timer (fictício, no estilo dos do ESP32) que usaremos no resto do capítulo:

     31            16 15         8 7    4 3   2   1      0
┌────────────────┬────────────┬──────┬─────┬───────┬────┐
│   (reservado)  │  DIVISOR   │ (res)│MODO │RECARGA│ EN │
└────────────────┴────────────┴──────┴─────┴───────┴────┘

    Três funções resolvem qualquer campo. Primeiro, a máscara: largura bits ligados a partir do bit 0.

    constexpr uint32_t mascara(unsigned largura) {
    return largura >= 32 ? 0xFFFF'FFFFu : (1u << largura) - 1u;
}

    O caso de 32 bits é separado porque deslocar um valor de 32 bits por 32 posições não é permitido em C++ (o resultado é indefinido, e cada compilador faz uma coisa). Com a máscara, extrair é deslocar e isolar; gravar é limpar a faixa e só então colocar o valor novo:

    constexpr uint32_t extrai_campo(uint32_t valor, unsigned pos, unsigned largura) {
    return (valor >> pos) & mascara(largura);
}

constexpr uint32_t grava_campo(uint32_t valor, unsigned pos, unsigned largura, uint32_t novo) {
    uint32_t m = mascara(largura) << pos;
    return (valor & ~m) | ((novo << pos) & m);
}

    Por que limpar antes? exemplos/cap05_campos.cpp parte de um registrador com divisor 3 e tenta gravar 4 das duas formas (as saídas estão em hexadecimal):

    uint32_t ctrl = 0x0000'0301;     // divisor 3 (bits 8-15), EN ligado (bit 0)
uint32_t errado = ctrl | (4u << 8);              // sem limpar o campo antes
uint32_t certo = grava_campo(ctrl, 8, 8, 4);
uint32_t grande = grava_campo(ctrl, 8, 8, 0x1FF);  // nao cabe em 8 bits

    divisor          3
com |= so        7
com grava_campo  4
registrador      401
valor grande     ff01

    Só com OU, os bits do 3 (011) e do 4 (100) se misturaram e viraram 7. E o & m final em grava_campo impede que um valor grande demais (0x1FF tem 9 bits) transborde para o campo vizinho: o divisor ficou ff, e o resto do registrador não foi tocado.

    constexpr e static_assert: o compilador confere as contas¶

    As três funções acima são constexpr: se os argumentos forem conhecidos durante a compilação, o compilador faz a conta e o programa já nasce com o resultado. Isso permite uma coisa que um assert comum não faz: conferir a conta antes de o programa existir.

    static_assert(mascara(4) == 0xFu, "mascara de 4 bits");
static_assert(mascara(32) == 0xFFFF'FFFFu, "mascara do registrador inteiro");
static_assert(extrai_campo(0x0000'0A00u, 8, 8) == 0x0Au, "divisor nos bits 8-15");

    Se alguma das condições for falsa, o arquivo não compila, e a mensagem aparece no erro. Em firmware isso vale ouro: uma máscara errada descoberta na compilação não chega à placa. (O static_assert é a ferramenta do capítulo, mas ele não substitui os testes com assert: só confere o que se sabe durante a compilação.)

    enum class para os valores de um campo¶

    O campo MODO aceita três valores. Com um int, nada impede de gravar 3, ou 7, ou o divisor no lugar do modo. O enum class do capítulo 4 resolve, agora com o tipo de baixo escolhido:

    enum class Modo : uint32_t { Sobe = 0, Desce = 1, SobeDesce = 2 };

    O : uint32_t diz que cada valor é guardado como um uint32_t, o tipo do registrador. Uma função que recebe Modo só aceita Modo::Sobe, Modo::Desce ou Modo::SobeDesce. Passar um número dá erro de compilação:

    error: cannot convert ‘int’ to ‘Modo’

    Para gravar no registrador, a conversão é explícita: static_cast<uint32_t>(m). Ela fica escrita num lugar só, dentro da classe, e não espalhada pelo programa.

    A classe Registrador32¶

    Juntando tudo: uma classe que guarda uma referência para a palavra de 32 bits e oferece as operações com nome.

    // Um registrador de 32 bits, visto por metodos com nome.
// Guarda uma REFERENCIA: mexe na variavel de fora, nao numa copia.
class Registrador32 {
private:
    uint32_t& valor_;

public:
    explicit Registrador32(uint32_t& valor) : valor_(valor) {}

    void liga(unsigned bit) { valor_ |= (1u << bit); }
    void desliga(unsigned bit) { valor_ &= ~(1u << bit); }
    void inverte(unsigned bit) { valor_ ^= (1u << bit); }
    bool testa(unsigned bit) const { return (valor_ >> bit) & 1u; }

    uint32_t campo(unsigned pos, unsigned largura) const {
        return (valor_ >> pos) & mascara(largura);
    }
    void grava_campo(unsigned pos, unsigned largura, uint32_t novo) {
        uint32_t m = mascara(largura) << pos;
        valor_ = (valor_ & ~m) | ((novo << pos) & m);
    }

    uint32_t valor() const { return valor_; }
};

    Por que referência (uint32_t&) e não uma cópia (uint32_t)? Porque o registrador mora fora do objeto: hoje é uma variável do programa, no capítulo 6 será um endereço do chip. A classe não é dona do valor, só oferece uma forma segura de mexer nele. Um membro referência também tem uma consequência que o compilador cobra: ele precisa ser ligado a uma variável de verdade. Registrador32 r(0x3FF44004u); não compila:

    error: cannot bind non-const lvalue reference of type ‘uint32_t&’ {aka ‘unsigned int&’} to an rvalue of type ‘uint32_t’ {aka ‘unsigned int’}

    Um número solto não é um lugar onde se possa escrever. Guarde essa mensagem: o capítulo 6 resolve exatamente isso, transformando um endereço numa referência.

    Dando nome aos campos: ConfigTimer¶

    O Registrador32 ainda fala em "bit 0" e "campo 8, 8". O passo final é uma classe que conhece o mapa daquele registrador e fala a língua do problema:

    enum class Modo : uint32_t { Sobe = 0, Desce = 1, SobeDesce = 2 };

class ConfigTimer {
private:
    static constexpr unsigned BIT_EN = 0;
    static constexpr unsigned BIT_RECARGA = 1;
    static constexpr unsigned POS_MODO = 2, LARG_MODO = 2;
    static constexpr unsigned POS_DIVISOR = 8, LARG_DIVISOR = 8;
    static_assert(POS_DIVISOR + LARG_DIVISOR <= 32, "campo passa do bit 31");

    Registrador32 reg_;

public:
    explicit ConfigTimer(uint32_t& registrador) : reg_(registrador) {}

    void habilita() { reg_.liga(BIT_EN); }
    void desabilita() { reg_.desliga(BIT_EN); }
    void recarga(bool sim) { if (sim) { reg_.liga(BIT_RECARGA); } else { reg_.desliga(BIT_RECARGA); } }
    void modo(Modo m) { reg_.grava_campo(POS_MODO, LARG_MODO, static_cast<uint32_t>(m)); }
    void divisor(uint8_t d) { reg_.grava_campo(POS_DIVISOR, LARG_DIVISOR, d); }

    bool habilitado() const { return reg_.testa(BIT_EN); }
    uint8_t divisor() const { return static_cast<uint8_t>(reg_.campo(POS_DIVISOR, LARG_DIVISOR)); }
};

    Três escolhas que valem para qualquer registrador:

    1. O mapa mora num lugar só. As posições são constantes static constexpr privadas: quem usa ConfigTimer nunca vê um número de bit.
    2. Os tipos protegem os valores. O divisor é uint8_t porque o campo tem 8 bits; o modo é Modo. Valor errado não compila.
    3. Composição. ConfigTimer tem um Registrador32 (capítulo 3) e só usa a interface pública dele.

    Usando (exemplos/cap05_registrador.cpp):

    uint32_t ctrl = 0;               // no capitulo 6, isto vira um endereco do chip
ConfigTimer timer(ctrl);

timer.divisor(80);
timer.modo(Modo::SobeDesce);
timer.recarga(true);
timer.habilita();

    ctrl = 0x500b
habilitado 1
divisor    80
ctrl = 0x500a

    O 0x500b é exatamente o "número mágico" do começo do capítulo: divisor 80 (0x50) nos bits 8–15, modo 2 nos bits 2–3, recarga e EN ligados. A diferença é que ninguém precisou escrevê-lo, e quem lê o código vê timer.divisor(80). Depois de desabilita(), só o bit 0 mudou (0x500a).

    O mesmo Registrador32, copiado sem mudar uma linha para um sketch no Wokwi, imprime ctrl = 0x500B no Monitor Serial. É a regra do curso desde o capítulo 1: a classe roda igual no computador e na placa.

    Padrão de projeto: registrador tipado

    Esconder um registrador atrás de uma classe que dá nome e tipo a cada campo é a ideia que Christopher Kormanyos desenvolve no capítulo sobre acesso a registradores do livro Real-Time C++ (o nome "registrador tipado" é do curso). Em vez de máscaras espalhadas pelo programa, um lugar só conhece o mapa de bits, e o compilador recusa valores que não cabem (Modo em vez de int, uint8_t para um campo de 8 bits).

    O ganho aparece no capítulo 6: lá, o Registrador32 passa a apontar para um endereço real do ESP32 e vira a base do Hardware Proxy que você conheceu no capítulo 1, sem que quem usa a classe perceba a troca.

    Erros comuns¶

    if (reg & 0x04 == 0) sempre dá o mesmo resultado. O == tem precedência maior que o &: o compilador lê reg & (0x04 == 0), ou seja, reg & 0. Ele avisa, se os avisos estiverem ligados: suggest parentheses around comparison in operand of '&'. Escreva (reg & 0x04) == 0, ou use testa().

    ~ num uint8_t não dá o que parece. Com uint8_t m = 0x0F, a expressão ~m == 0xF0 é falsa. Antes de qualquer conta, o C++ promove o uint8_t para int, e ~m vira -16 (32 bits ligados menos os 4 de baixo). O compilador avisa (comparison of promoted bitwise complement of an unsigned value with constant). Converta de volta: static_cast<uint8_t>(~m) == 0xF0.

    reg = 1u << n no lugar de reg |= 1u << n. O = zera todos os outros bits. Num registrador de GPIO, isso desliga todos os outros pinos.

    Gravar um campo só com |=. Os bits antigos do campo continuam lá e se misturam com os novos. Limpe antes (grava_campo).

    Deslocar demais. 1 << 35 não cabe em 32 bits: o compilador avisa left shift count >= width of type, e o resultado é indefinido. Para 64 bits, 1ull << 35. Num registrador de 32 bits, posições vão de 0 a 31.

    std::cout << meu_uint8 imprime uma letra. É o std::cout tratando uint8_t como char. Use +meu_uint8.

    Resumo¶

    • int e long mudam de tamanho entre plataformas (long: 8 bytes no PC, 4 no ESP32). Para registradores e dados de hardware, use <cstdint>: uint32_t para registrador.
    • Mexer num bit sem tocar nos outros: |= liga, &= ~ desliga, ^= inverte, (reg >> n) & 1u testa. Sempre 1u, nunca 1.
    • Campo de vários bits: extrair é (v >> pos) & mascara; gravar é limpar e depois colocar, cortando o valor novo com a máscara.
    • Funções constexpr deixam o compilador fazer a conta; static_assert confere durante a compilação.
    • enum class X : uint32_t restringe os valores de um campo; a conversão static_cast fica num lugar só.
    • Registrador tipado: Registrador32 guarda uma referência para a palavra e dá nome às operações; uma classe como ConfigTimer conhece o mapa de bits e fala a língua do problema.
