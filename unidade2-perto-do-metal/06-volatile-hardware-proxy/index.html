    6. volatile e Hardware Proxy¶

    Vídeo

    Ainda não há vídeo para este capítulo.

    Desde o capítulo 1, o Led chama digitalWrite e o pino muda. Neste capítulo abrimos essa caixa: por baixo do digitalWrite há registradores, palavras de 32 bits em endereços fixos do ESP32, e escrever neles diretamente é muitas vezes mais rápido. Para fazer isso com segurança, três coisas novas entram em cena: transformar um endereço numa referência (o erro que o capítulo 5 deixou pendurado), avisar o compilador com volatile de que aquela memória é especial, e esconder tudo isso numa classe, o Hardware Proxy, para que o resto do programa nem perceba a troca.

    E, para saber se valeu a pena, aprendemos a medir tempo em microssegundos. É o primeiro contato do curso com a pergunta que domina as Unidades 3 e 4: quanto tempo isso leva?

    O problema: o que há debaixo do digitalWrite¶

    O digitalWrite(26, HIGH) do core Arduino faz algumas coisas antes de mudar o pino: confere se aquele pino foi mesmo configurado como GPIO e passa o pedido adiante para uma função do ESP-IDF. Tudo isso para, no fim, mudar um bit numa palavra de 32 bits do chip.

    Na maior parte do tempo, esse custo não importa. Mas há situações em que importa: gerar um sinal rápido, mudar vários pinos no mesmo instante, ler um pino dentro de uma interrupção (capítulo 9). Nesses casos, quem escreve firmware vai direto ao registrador. E aí surgem três perguntas:

    1. Onde ficam os registradores e o que cada bit significa?
    2. Como um programa C++ escreve num endereço fixo?
    3. Como garantir que o compilador não "otimize" essas escritas para fora do programa?

    Os registradores de GPIO do ESP32¶

    O manual técnico do ESP32 (e o cabeçalho soc/gpio_reg.h do ESP-IDF, que o core Arduino usa) lista os registradores do periférico GPIO. Os que interessam aqui:

    Registrador Endereço O que faz
    GPIO_OUT_REG 0x3FF4'4004 o nível de saída dos pinos 0 a 31, um bit por pino
    GPIO_OUT_W1TS_REG 0x3FF4'4008 escrever 1 num bit liga aquele pino (write 1 to set)
    GPIO_OUT_W1TC_REG 0x3FF4'400C escrever 1 num bit desliga aquele pino (write 1 to clear)
    GPIO_IN_REG 0x3FF4'403C o nível lido nos pinos 0 a 31
    GPIO_OUT1_W1TS_REG 0x3FF4'4014 o mesmo W1TS, para os pinos 32 a 39
    GPIO_OUT1_W1TC_REG 0x3FF4'4018 o mesmo W1TC, para os pinos 32 a 39
    GPIO_IN1_REG 0x3FF4'4040 o nível lido nos pinos 32 a 39 (pino 32 = bit 0)

    Dois detalhes desta tabela mudam o jeito de programar.

    W1TS e W1TC dispensam o "ler, mexer, escrever". Com o GPIO_OUT_REG, ligar o pino 26 seria out |= (1u << 26): ler a palavra, ligar um bit, escrever de volta. São três passos, e se uma interrupção mudar outro pino no meio deles, a escrita final desfaz a mudança dela. Os registradores W1TS e W1TC existem para evitar isso: neles, bit 0 não muda nada. Então se escreve com =, numa operação só:

    w1ts = (1u << 26);    // liga o 26; todos os outros pinos ficam como estavam
w1tc = (1u << 26);    // desliga o 26

    Repare que é o contrário da regra do capítulo 5, onde = apagava os outros bits. Aqui o hardware foi desenhado para que = seja o certo. É por isso que se lê o manual de cada registrador.

    Os pinos ficam em dois bancos. Uma palavra de 32 bits só cobre 32 pinos, e o ESP32 tem GPIO até o 39. Os pinos 0 a 31 ficam no "banco 0"; os 32 a 39, no "banco 1", em outros registradores, a partir do bit 0. O botão A do curso, no pino 32, é o bit 0 do GPIO_IN1_REG.

    Os registradores mudam o nível do pino, mas não o configuram como saída. Essa parte continua com o pinMode do Arduino, chamado uma vez no inicia(). É a divisão de trabalho do capítulo: a configuração, que acontece uma vez, fica com a API do Arduino; o caminho rápido, que acontece toda hora, vai direto ao registrador.

    Do endereço à referência¶

    O capítulo 5 terminou com este erro:

    error: cannot bind non-const lvalue reference of type ‘uint32_t&’ {aka ‘unsigned int&’} to an rvalue of type ‘uint32_t’ {aka ‘unsigned int’}

    Um número não é um lugar onde se possa escrever. Para o C++ tratar 0x3FF4'4008 como um lugar, é preciso dizer explicitamente "este número é o endereço de um uint32_t" e então seguir esse endereço:

    // Transforma um endereco do chip numa referencia para um registrador.
inline volatile uint32_t& registrador(uint32_t endereco) {
    return *reinterpret_cast<volatile uint32_t*>(endereco);
}

    Lendo de dentro para fora:

    1. reinterpret_cast<volatile uint32_t*>(endereco) diz ao compilador: "confie em mim, este número é um ponteiro para um uint32_t". É a conversão mais perigosa do C++ (ele não confere nada), e por isso tem um nome longo e fácil de procurar no código. Ela deve aparecer num lugar só do programa.
    2. O * na frente segue o ponteiro: o resultado é o próprio registrador.
    3. A função devolve uma referência a ele, que pode ser guardada num membro, exatamente como o Registrador32 do capítulo 5 guardava a referência para uma variável.

    Falta explicar a palavra nova, que aparece em todo lugar: volatile.

    volatile: o compilador não pode "economizar"¶

    O compilador otimiza o programa supondo que só o programa mexe na memória. Se você escreve duas vezes o mesmo valor numa variável sem ninguém ler no meio, a primeira escrita é inútil e pode sumir. Se você lê a mesma variável num laço sem mudá-la, o valor não muda e basta ler uma vez. Para memória comum, essas suposições são verdadeiras e deixam o programa mais rápido.

    Para um registrador, são falsas. Cada escrita no W1TS muda um pino: duas escritas são duas mudanças. E o GPIO_IN1_REG muda sozinho quando alguém aperta o botão, sem o programa encostar nele.

    Veja o que o compilador do ESP32 (o mesmo GCC 14 do core Arduino, com otimização ligada) faz com este código, que pisca o pino 26 duas vezes sem volatile:

    void pisca_sem_volatile() {
    uint32_t* w1ts = reinterpret_cast<uint32_t*>(0x3FF44008);
    uint32_t* w1tc = reinterpret_cast<uint32_t*>(0x3FF4400C);
    *w1ts = 1u << 26;
    *w1tc = 1u << 26;
    *w1ts = 1u << 26;
    *w1tc = 1u << 26;
}

    O assembly gerado (trecho, com comentários nossos):

    l32r    a8, .LC1        ; a8 = 1 << 26
l32r    a9, .LC0        ; a9 = endereco do W1TS
s32i    a8, a9, 0       ; uma escrita no W1TS
l32r    a9, .LC2        ; a9 = endereco do W1TC
s32i    a8, a9, 0       ; uma escrita no W1TC
retw.n

    Quatro escritas no código, duas no programa. O LED pisca uma vez, não duas. Com volatile uint32_t* no lugar de uint32_t*, as quatro voltam, cada uma precedida de memw (uma instrução do Xtensa que faz o processador terminar os acessos à memória anteriores antes de começar o próximo):

    memw
s32i    a8, a10, 0      ; W1TS
memw
s32i    a8, a9, 0       ; W1TC
memw
s32i    a8, a10, 0      ; W1TS
memw
s32i    a8, a9, 0       ; W1TC

    O caso da leitura é ainda mais drástico. Esta função espera o botão (pino 32) ser apertado:

    bool espera_sem_volatile() {
    uint32_t* in1 = reinterpret_cast<uint32_t*>(0x3FF44040);
    while ((*in1 & 1u) != 0) { }      // enquanto o bit 0 estiver em 1, espera
    return true;
}

    Sem volatile, o compilador gerou isto:

    movi.n  a2, 1           ; devolve true
retw.n

    O laço sumiu. Do ponto de vista do compilador, nada dentro do laço muda *in1, então ou ele nunca roda, ou roda para sempre, e um laço infinito sem efeito nenhum não é um programa válido em C++. Com volatile, o laço volta e relê o registrador a cada volta:

    .L6:
memw
l32i    a8, a9, 0       ; le o GPIO_IN1
bbsi    a8, 0, .L6      ; bit 0 ainda em 1? volta

    A regra: toda memória que o hardware lê ou muda por conta própria é volatile. O volatile diz ao compilador: cada leitura e cada escrita que está no código tem que acontecer de verdade, na ordem em que foi escrita.

    E o compilador protege a regra depois que ela foi escrita. Guardar um registrador volatile numa referência comum não compila:

    error: binding reference of type ‘uint32_t&’ {aka ‘unsigned int&’} to ‘volatile uint32_t’ {aka ‘volatile unsigned int’} discards qualifiers

    "Discards qualifiers" quer dizer "você está jogando fora o volatile". É o mesmo tipo de proteção do const: uma vez marcado, não se perde sem querer.

    volatile não resolve tudo

    volatile garante que o acesso acontece; ele não garante que um "ler, mexer, escrever" seja feito sem interrupção no meio, nem que duas tarefas não pisem uma na outra. Essa é outra história, com outras ferramentas: seções críticas no capítulo 9 e mutex no capítulo 15.

    O Hardware Proxy: LedRapido e EntradaRapida¶

    Agora juntamos tudo numa classe. Primeiro, um struct que agrupa os três registradores de um banco, como referências volatile:

    // Os tres registradores de um banco de GPIO. O ESP32 tem dois bancos:
// o 0 cobre os pinos 0 a 31; o 1, os pinos 32 a 39 (pino 32 = bit 0).
// volatile: cada leitura e cada escrita tem que acontecer de verdade.
struct BancoGpio {
    volatile uint32_t& saida_liga;      // W1TS: escrever 1 num bit LIGA aquele pino
    volatile uint32_t& saida_desliga;   // W1TC: escrever 1 num bit DESLIGA aquele pino
    volatile uint32_t& entrada;         // IN: o nivel atual de cada pino
};

    Depois, um LED que escreve nesses registradores, com a mesma interface do Led do capítulo 1:

    // Um LED por registrador. Mesma interface do Led do capitulo 1.
class LedRapido {
private:
    BancoGpio& banco_;
    const int pino_;
    const uint32_t mascara_;
    bool ligado_;

public:
    LedRapido(BancoGpio& banco, int pino)
        : banco_(banco), pino_(pino), mascara_(1u << (pino % 32)), ligado_(false) {}

    void inicia() { pinMode(pino_, OUTPUT); desliga(); }

    // "=" e nao "|=": nos registradores W1TS/W1TC, bit 0 nao muda nada.
    void liga() { banco_.saida_liga = mascara_; ligado_ = true; }
    void desliga() { banco_.saida_desliga = mascara_; ligado_ = false; }
    void alterna() { if (ligado_) { desliga(); } else { liga(); } }
    bool esta_ligado() const { return ligado_; }
};

    E uma entrada lida direto do registrador IN:

    // Um pino de entrada lido direto do registrador IN.
class EntradaRapida {
private:
    BancoGpio& banco_;
    const int pino_;
    const uint32_t mascara_;

public:
    EntradaRapida(BancoGpio& banco, int pino)
        : banco_(banco), pino_(pino), mascara_(1u << (pino % 32)) {}

    void inicia() { pinMode(pino_, INPUT_PULLUP); }

    bool nivel_alto() const { return (banco_.entrada & mascara_) != 0; }
};

    As convenções do curso continuam valendo: o construtor só guarda configuração (inclusive a máscara, calculada uma vez), e inicia() mexe no hardware. O pino % 32 dá a posição do pino dentro do banco: o 26 é o bit 26 do banco 0; o 32 é o bit 0 do banco 1.

    Os endereços moram num arquivo separado, gpio_esp32.h, e só ele conhece o chip:

    //                         W1TS (liga)              W1TC (desliga)           IN (entrada)
inline BancoGpio gpio0 = { registrador(0x3FF44008), registrador(0x3FF4400C), registrador(0x3FF4403C) };
inline BancoGpio gpio1 = { registrador(0x3FF44014), registrador(0x3FF44018), registrador(0x3FF44040) };

    (O inline numa variável, do C++17, permite defini-la num .h incluído por vários arquivos sem gerar "definição duplicada".)

    O sketch do projeto wokwi/cap06-registrador/ usa a bancada do capítulo 3:

    Esquemático de cap06-registrador: três LEDs com resistor e o botão A no pino 32.

    #include "gpio_esp32.h"
#include "temporizador.h"

LedRapido vermelho(gpio0, 26);       // pino 26: banco 0, bit 26
LedRapido amarelo(gpio0, 27);
EntradaRapida botao_a(gpio1, 32);    // pino 32: banco 1, bit 0
Temporizador meio_segundo(500);

bool estava_apertado = false;

void setup() {
    Serial.begin(115200);
    vermelho.inicia();
    amarelo.inicia();
    botao_a.inicia();
    meio_segundo.reinicia();
    Serial.println("GPIO por registrador");
}

void loop() {
    if (meio_segundo.expirou()) {
        vermelho.alterna();
    }

    // Com pull-up, apertado e nivel BAIXO.
    bool apertado = !botao_a.nivel_alto();
    if (apertado) {
        amarelo.liga();
    } else {
        amarelo.desliga();
    }
    if (apertado != estava_apertado) {
        Serial.println(apertado ? "apertado" : "solto");
        estava_apertado = apertado;
    }
}

    Rode no Wokwi: o vermelho pisca a cada meio segundo e o amarelo acende enquanto o botão A está apertado, sem um único digitalWrite ou digitalRead no loop(). E o Monitor Serial mostra uma coisa que a Unidade 1 já conhece: um aperto só imprime várias linhas apertado/solto. O botão está quicando, e a leitura crua do registrador mostra cada quique. Ler mais rápido não resolve o quique; o BotaoFiltrado do capítulo 4 continua necessário (e funciona igual sobre uma EntradaRapida).

    O mesmo proxy, no computador¶

    No computador não existe o endereço 0x3FF4'4008. Mas o LedRapido não sabe disso: ele só conhece um BancoGpio. Basta montar um banco com variáveis volatile no lugar dos registradores (exemplos/cap06_proxy_no_host.cpp):

    volatile uint32_t w1ts = 0, w1tc = 0, in = 0;
BancoGpio gpio0{w1ts, w1tc, in};

LedRapido vermelho(gpio0, 26);
vermelho.inicia();
// imprime w1ts e w1tc
vermelho.liga();
// imprime de novo
EntradaRapida botao(gpio0, 27);
botao.inicia();
in = 1u << 27;          // o teste "aperta" mudando o registrador IN
// imprime nivel_alto()
in = 0;
// imprime nivel_alto()

    depois de inicia(): w1ts=0 w1tc=4000000
depois de liga():   w1ts=4000000 w1tc=4000000
nivel_alto com IN=8000000: 1
nivel_alto com IN=0: 0

    O inicia() chamou desliga(), que escreveu 0x0400'0000 (o bit 26) no W1TC. O liga() escreveu o mesmo bit no W1TS. Repare que w1tc continua com o valor antigo: as variáveis só lembram a última escrita, não se comportam como os registradores de verdade (o W1TC real não guarda nada). Para testar a classe, isso basta: o teste pergunta "o que você escreveu, e onde?". Esse tipo de substituto tem nome, e o capítulo 8 o apresenta.

    O único arquivo que muda entre a placa e o computador é o que monta os bancos. A classe é a mesma.

    Medir tempo: micros() e Cronometro¶

    Ir ao registrador é mais rápido. Quanto? Para responder, precisamos de um relógio mais fino que o millis(). O micros() devolve os microssegundos desde que a placa ligou, como unsigned long de 32 bits. Ele dá a volta a cada 2³² µs, uns 71 minutos, e a subtração sem sinal do capítulo 3 continua resolvendo isso.

    A medição vira uma classe pequena:

    class Cronometro {
private:
    uint32_t inicio_us_;

public:
    Cronometro() : inicio_us_(0) {}

    // Comeca a contar a partir de agora.
    void zera() { inicio_us_ = static_cast<uint32_t>(micros()); }

    // Microssegundos desde o ultimo zera(). A conta em 32 bits sem sinal
    // continua certa quando o micros() da a volta (a cada ~71 minutos).
    uint32_t decorrido_us() const { return static_cast<uint32_t>(micros()) - inicio_us_; }
};

    Por que uint32_t e não o unsigned long que o micros() devolve? No ESP32 os dois têm 32 bits e tanto faz. No computador, unsigned long tem 64 bits (capítulo 5), e a subtração deixaria de "dar a volta" junto com o relógio de 32 bits: o cronômetro funcionaria na placa e erraria no teste. Fazendo a conta em uint32_t, ela dá o mesmo resultado nas duas plataformas.

    O arduino_falso.h ganhou micros() e falso::avanca_micros(us), para testar no computador (exemplos/cap06_cronometro.cpp):

    Cronometro c;
falso::avanca_micros(1500);       // a placa ja estava ligada ha 1,5 ms
c.zera();
falso::avanca_micros(307);
// decorrido?
falso::avanca_tempo(2);           // mais 2 ms
// decorrido? millis? micros?

    decorrido: 307 us
decorrido: 2307 us
millis: 3  micros: 3807

    millis() e micros() olham o mesmo relógio: 3807 µs são 3 ms inteiros.

    Quanto custa cada operação¶

    O projeto wokwi/cap06-custos/ repete cada operação 1000 vezes entre um zera() e um decorrido_us(), e divide o tempo total pelo número de operações:

    cronometro.zera();
for (int i = 0; i < REPETICOES; i++) {
    digitalWrite(26, HIGH);
    digitalWrite(26, LOW);
}
mostra("digitalWrite         ", cronometro.decorrido_us(), 2 * REPETICOES);

    (e o mesmo para vermelho.liga()/desliga(), digitalRead(32) e botao_a.nivel_alto()). No Wokwi:

    --- custo medio (1000 repeticoes) ---
digitalWrite         7954 ns por operacao
LedRapido (W1TS/W1TC)307 ns por operacao
digitalRead          6527 ns por operacao
EntradaRapida (IN1)  739 ns por operacao

    No simulador, escrever pelo registrador saiu mais de 20 vezes mais barato que pelo digitalWrite, e ler, umas 9 vezes. Os números absolutos são do Wokwi, que não garante o tempo exato de cada instrução do chip: numa placa de verdade eles serão outros. O que a tabela ensina é a ordem de grandeza da diferença, e a forma de medir, que é a mesma em qualquer placa.

    Por que repetir 1000 vezes? Porque uma operação de algumas centenas de nanossegundos é menor que a resolução do micros() (1 µs). Medindo mil, o erro de um microssegundo se dilui.

    O mesmo projeto mede o Serial.print de dez caracteres, chamado 50 vezes seguidas, guardando o tempo da primeira chamada e o da pior:

    primeira chamada: 69 us
pior chamada:     11136 us

    A primeira chamada só copiou os caracteres para um buffer de saída e voltou. Quando o buffer encheu, as chamadas seguintes passaram a esperar a UART transmitir, e uma delas ficou parada mais de 11 ms. A mesma linha de código, com custos que variam de 160 vezes conforme o que aconteceu antes: é isso que torna o Serial.print perigoso num laço que precisa ser pontual. Essa variação tem nome, jitter, e volta com força no capítulo 12.

    Padrão de projeto: Hardware Proxy

    O Hardware Proxy (catálogo de Bruce Powel Douglass) é uma classe que fica no lugar de um periférico e é a única parte do programa que conhece seus endereços, seus bits e suas regras (como "nos W1TS, escreva com ="). Quem usa o proxy chama operações com nome, como liga() e nivel_alto().

    O Led do capítulo 1 já era um proxy, sobre a API do Arduino. O LedRapido é outro, sobre os registradores, com a mesma interface: trocar um pelo outro no sketch muda a velocidade e não muda a lógica. Por enquanto, essa troca é feita mudando o tipo na declaração. No capítulo 8, ela ganha uma forma melhor, com interfaces, e o programa passa a escolher o proxy sem que o resto do código saiba qual é.

    Erros comuns¶

    Esquecer o volatile. O programa compila e às vezes funciona, até a otimização apagar uma escrita repetida ou um laço de espera inteiro, como no assembly acima. Todo ponteiro ou referência para registrador é volatile.

    |= num W1TS ou W1TC. Esses registradores existem para serem escritos com =: o bit 0 não muda nada. O |= acrescenta uma leitura que não serve para nada e transforma uma operação única em três.

    O pino no banco errado. LedRapido(gpio0, 32) calcula a máscara 1u << (32 % 32), que é o bit 0 do banco 0: o programa mexe no pino 0, não no 32. Pinos de 32 a 39 vão no gpio1.

    Esquecer o inicia(). Sem o pinMode(OUTPUT), o pino não está habilitado como saída, e a escrita no W1TS não aparece no LED (conferido no Wokwi: o LED fica apagado o tempo todo). O mesmo sintoma do capítulo 1, por outro caminho.

    Medir uma operação só. Algumas centenas de nanossegundos não aparecem num relógio de 1 µs: o resultado vira 0 ou 1. Repita muitas vezes e divida.

    Medir com um Serial.print dentro do trecho medido. O tempo do print (que, como vimos, varia muito) entra na conta e esconde o que se queria medir. Meça primeiro, imprima depois.

    Resumo¶

    • Por baixo do digitalWrite há registradores de 32 bits em endereços fixos. No ESP32, GPIO_OUT_W1TS_REG liga e GPIO_OUT_W1TC_REG desliga pinos escrevendo 1 nos bits desejados, com = e sem ler antes. Os pinos 32 a 39 ficam num segundo banco de registradores.
    • *reinterpret_cast<volatile uint32_t*>(endereco) transforma um endereço numa referência para o registrador. A conversão fica num lugar só.
    • volatile obriga o compilador a fazer cada leitura e cada escrita que está no código. Sem ele, o compilador do ESP32 apagou escritas repetidas e um laço de espera inteiro.
    • Hardware Proxy: LedRapido e EntradaRapida são as únicas classes que conhecem os registradores, e o LedRapido tem a mesma interface do Led. Os endereços ficam num arquivo separado; no computador, variáveis volatile fazem o papel dos registradores.
    • micros() e a classe Cronometro medem microssegundos. Meça muitas repetições e divida; no Wokwi, o registrador saiu dezenas de vezes mais barato que o digitalWrite, e o Serial.print mostrou um custo que varia muito: jitter.
